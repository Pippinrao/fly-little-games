# 三端双向附近联机最小可玩设计

日期：2026-09-21；2026-09-23 同步范围更新。实现基线：`origin/main@612f76d`。
最初范围只覆盖 Android 房主/P1 → HarmonyOS 客机/P2。2026-09-23 用户授权把
**同一个最小可玩实现**同步到 Android、HarmonyOS NEXT、iOS，并让每端均可作为
房主/P1 或客机/P2。该授权只覆盖平台与角色方向；本文其余最小可玩约束继续有效。

## 0. 2026-09-23 三端同步边界

- 不改变现有 UX 设计。三端继续使用已有“创建联机 / 扫码加入”入口、大厅、单机
  游戏页、手柄和暂停抽屉；只替换尚未接入真实会话的占位行为与硬编码角色文案。
- 不新增协议或第二套 owner。三端统一调用 `fly_lan_mvp_host` / `fly_lan_mvp_join`，
  并从 `fly_lan_mvp_snapshot.role` 读取本端角色。房主始终是 P1，客机始终是 P2。
- 不改变 Android 房主 → HarmonyOS 客机已有行为。共享协议、线格式、邀请格式、
  ROM/config 摘要、锁步输入、暂停、回大厅、同连接换游戏和错误收敛保持兼容。
- 新接的反向与 iOS 方向先以双方已有的首个合格内置游戏完成接线；导入 ROM 对称查找、
  新房主游戏选择和新方向同连接换游戏不在本次同步中补齐，也不据此宣称完整功能。
- iOS 复用现有 Nearby 页面与 `RunGameView`/`RunSurfaceViewController`，增加最薄的
  ObjC++ 会话桥；Android/Harmony 只补齐各自缺失的 host 或 join owner 接线。
- 扫码结果消费、真实网络、ROM/核心、P1/P2 输入、画面/PCM 和生命周期必须在模拟器
  覆盖；摄像头取景、真实热点、物理触控/扬声器和物理端到端延迟留给硬件验收。

实现的对称性目标是 A→H、H→A、A→I、I→A、H→I、I→H，其中箭头左侧为房主/P1，
右侧为客机/P2。本次工作只同步现有最小可玩接线，不把六方向完整验收、全部异常恢复或
物理设备矩阵扩成当前交付；未实际运行的组合不得从 ABI、构建或平台内测试推断为已通过。

## 1. 交付结果

2026-09-22 首条产品路径为 Android 房主/P1 手动开启个人热点，HarmonyOS 客机/P2
手动加入该热点；2026-09-23 起任意平台可创建房间并展示二维码，任意另一平台可扫码
加入。普通路由器兼容仍排后；不增加自动组网。
既有 Android 房主路径选择游戏并展示二维码；本次新增房主路径自动选择首个合格内置
游戏。客机消费扫码结果加入，双方确认游戏后开始。
两端各运行一份真实 NES 核心，各自的触屏按键控制各自的玩家；两端都有画面和声音。

2026-09-22 用户指定用本地《雪人兄弟》验收；内置双人游戏用于换游戏回归。
通过现有内容清单和目录选择它，产品代码不得写入游戏名称、ID、文件名或特殊分支。
私人 ROM 由现有游戏库导入，不放入仓库内容包；不扩展成全 ROM 兼容项目。

完成标准：两个真实平台 App 经唯一扫码入口完成一局可交互的游戏，连续试玩
10 分钟；分别操作 P1/P2 都能在两端观察到相同的动作结果；退出或断网后双方
停止推进，不继续各玩各的。真实设备证据到位才记录“附近联机最小可玩完成”。
模拟器、主机双实例和编译成功分别记录自己的边界。

## 3. 架构取舍

清理后的代码已经有真实 NES runtime、Quinn/rustls C ABI、输入/摘要实现和两端
UI 骨架。产品发现仍未接通，Harmony 的 V2 owner 尚未连接到 UI 和运行器。
旧 `SessionEngine` 的配对、持久身份、承载协商和恢复调度绑定较深，继续把所有
端口补齐当作开局条件，会再次扩大首版。

采用一个小的共享 **LAN MVP 会话协调器**：复用现有 QUIC provider 和 `fly_runtime_*`，
只编排本轮配对、开局和逐帧输入。它位于 `shared/src/session/lan_mvp/`，通过一个
小型 C ABI 给 JNI/N-API 调用。Android/Harmony 只提供网络地址、扫码/UI、按键、
画面和音频接线。协调器接管附近联机产品路径后，旧完整 engine 不再同时创建或推进。

这是替换产品编排入口的有限改动。NES 核心、QUIC/TLS、目录、渲染算法均沿用。
旧 engine、协议和恢复模块作为历史实现保留在主干及其测试中；不用为了复用这些模块，
给 MVP 制造假的认证事件、假持久化或假平台端口。

```text
Android host/join ─ JNI ─────┐
Harmony host/join ─ N-API ───┼─ shared LAN MVP coordinator ─ 已有 QUIC C ABI
iOS host/join ─ ObjC++ ──────┘                 │
                               已有 fly_runtime_* / NestopiaUE
                                            │
                              各端既有画面显示与 PCM 播放
```

每端只有一个联机会话 owner、一个 runtime 和一个推进核心的线程。
触屏只提交本地输入；渲染和音频回调只消费输出，不再推进第二份核心。
未来扩展保留协议版本和平台边界即可，不提前实现通用 provider 框架或未来状态机。

## 4. 唯一扫码路径

1. Android 选择本地游戏、取得可达局域网地址，调用现有 QUIC provider 生成
   临时 TLS 材料并监听真实网卡。监听/连接不可继续写死 `127.0.0.1`。
2. 生成邀请 QR，载荷包含协议版本、IPv4/端口、SHA-256(DER-SPKI) 和一个
   128 位随机单次邀请 token。邀请在房主单调时钟上 120 秒过期，重新建房替换旧邀请。
3. Harmony 的原生扫码结果直接交给共享邀请解析器。拒绝错误格式、未知版本和
   不支持的地址；不通过第三方网站或联网服务解码。
4. 客机用邀请中的 pin 建立真实 TLS/QUIC，并在加密连接内提交 token。
   房主核对未过期的单次 token 后接纳唯一客机，清除可再次加入的邀请。
5. 交换游戏内容摘要与核心兼容标识，双方分别确认后开局。

临时证书与邀请只活在本次会话中，不需要好友数据库或持久密钥。
扫码带入的 pin 仍须真实校验；不关闭 TLS 验证。二维码载荷和 token 不写入日志。
失败显示可操作原因：未连接同网、邀请过期、游戏不匹配、版本不匹配或连接失败。
用户可以重新建房；首版不自动选择第二种连接路线。

## 5. 最小会话与数据流

状态为 `IDLE → INVITING/JOINING → LOBBY → CONFIGURING → RUNNING`。
游戏内复用 Android `MainActivity` 和 Harmony `RunGame`、原手柄与暂停抽屉。
暂停同步冻结双方核心；返回大厅经 `RETURNING` 清空旧局输入并保留连接及会话 ID。
房主从既有游戏库换游戏，客机按游戏身份读取本地 ROM，重新双确认后开新局，无需扫码。
缺少或不匹配 ROM 留在大厅并说明原因。只有主动断开或实际传输失败进入 `ENDED`。
后台暂停游戏；操作系统杀进程、网络消失后的自动恢复仍不属于本轮。

QUIC 使用一个可靠双向应用流，帧以显式长度分包。MVP 使用独立协议版本/标识，
和旧完整会话消息不混解。仅实现下列本轮消息：

| 消息 | 内容与作用 |
|---|---|
| JOIN / ACCEPT | 单次 token、会话 ID；确认对端获准进入本房间 |
| CONFIG | ROM 内容 SHA-256、核心兼容 ID、实际源帧率、采样率、固定 P1/P2 |
| READY / START | 双方确认同一配置摘要；双方加载新游戏后从同一 frame 0 开始 |
| PAUSE | 同步暂停/继续；暂停期间不触发游戏输入停顿超时 |
| LOBBY_REQUEST / LOBBY / LOBBY_ACK | 回大厅及旧局消息清空屏障，保留已认证连接 |
| INPUT | 会话 ID、帧号、本端按键；座位由连接角色决定，远端不能提交本端座位 |
| DIGEST | 每 60 个已完成帧的核心状态摘要；不一致就结束本局并记录原因 |
| END | 结束原因；网络关闭/超时也收敛到同一终止处理 |

使用 `fly_runtime_load_rom_fresh`，不继承单机存档、旧音频或按键。
CONFIG 的核心兼容 ID 由构建时核心版本和确定性配置产生，不以平台名字代替兼容性。
ROM 内容摘要、核心兼容 ID、源时序不一致时不进入 RUNNING。

首版采用确定性锁步：固定 2 帧输入缓冲，起始缓冲填零；按
`fly_runtime_get_source_timing` 的实际节拍采样本端未来帧输入并发送。
只有同一帧的 P1/P2 输入都到齐，才调用一次 `fly_runtime_step_frame`。
缺输入就等待，不预测，不用本地按键替代远端输入。队列使用有界帧窗口，网络回调
交给同一个 owner 处理；不引入另一条单机推进循环。

运行且未暂停时，2 秒没有收到下一帧所需的对端进展则结束会话。终止后清输入、停止核心推进和
音频生产、关闭连接并等待已接纳回调释放资源。只覆盖这条实际使用的关闭路径，
不把所有旧 engine 取消/恢复矩阵重新做一遍。

## 6. 可复用代码与本轮改动范围

| 代码 | 本轮用途 |
|---|---|
| `shared/nearby-quic-provider/` | 直接复用临时 TLS、pin、连接、双向流、关闭 C ABI |

| 新 `shared/src/session/lan_mvp/` | 小型邀请解析、消息编解码、会话协调和锁步队列 |
| Android `nearby/session_owner.*` 与 JNI、Nearby 页面 | 同一 owner 支持 host/join；既有页面按 snapshot role 显示 P1/P2 |
| Harmony N-API、`NearbyService.ets`、Nearby 页面、`native_play_runtime.*` | 同一 owner 支持 host/join；既有页面按 snapshot role 显示 P1/P2 |
| iOS ObjC++ bridge、Nearby 页面、现有运行页 | 接入同一 C ABI、邀请 QR/扫码结果和同一个联机 runtime 输出 |

只修改这条调用链。旧代码不做大规模搬迁或重构，UI 保留现有组件，隐藏本轮不可用入口。
协议/schema 的旧黄金文件不因 MVP 新消息批量重写。
