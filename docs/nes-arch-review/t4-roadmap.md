# t4 评估：演进路线与范围裁剪（roadmap 视角）

> 领域：产品范围与演进路线（MVP/基座最小范围、阶段优先级与依赖、里程碑切分、内置 homebrew 选型、魔改/上架/移植的前置条件与时机）。
> 团队结论聚焦三件事：①基座该多薄；②阶段边界如何重切；③内置 homebrew 选哪些。
> 注：本文件涉及 license 的候选仅为「产品侧选型建议」，最终再分发许可清点由 compliance（t5）负责。

---

## 0. 一句话结论

**「基座」应该比现路线更薄，且薄在「功能」上、厚在「接口」上。**
现路线的阶段 0 写着「Java 壳最小可玩（load ROM→渲染→触屏→声音→存档）」，容易让人把精力花在把体验做顺，而不是把 C ABI 做全。既然用户明说「不追求一次性成品、不着急上手玩」，那么基座的正确 DOD 是：

- **接口完备**：C ABI 一次性覆盖 load/run/input/video/audio/state/battery/cheat/patch/memory（以及 FDS/NSF 的占位），未实现的部分返回 not-implemented，而不是随阶段后补。
- **功能只 spike 一次**：每一类能力（渲染、音频、输入、存档）各跑通一条最小路径即可，不做完整打磨。
- **必须「架构验收」真玩**：至少一个内置 ROM 连续跑 5 分钟不爆音、不撕裂、不丢帧——这不是「产品验收」，是验证渲染格式/音频同步/时序假设的「架构验收」。

同时把三条轨道拆开：**功能演进（0→1→2）**、**上架/合规（独立轨道，应提前启动）**、**移植（独立轨道，需在基座阶段做 spike 验证）**。现路线把「上架」和「移植」捆进阶段 3，会同时拖延 GPL 决策和「只换壳」假设的验证。

## 1. 按优先级排序的拷问问题 / 决策点清单

### P0 —— 决定基座 DOD，必须先答

#### Q1. 基座的「完成定义（DOD）」到底是什么？
- **为什么重要**：这是所有路线讨论的根。没有可验收的 DOD，「基座做完」就永远是模糊的，阶段 1 会不断被「基座遗留项」污染。
- **选项与取舍**：
  - A. 只编出 `libnestopia.so` + 一个空壳 Activity —— 最快，但验证不了渲染/音频/时序，等于没验证。
  - B. 最小可玩垂直切片（1 个内置 ROM 跑通）—— 能验证，但若只求「能玩」，容易漏掉 ABI 完备性。
  - C. 架构闭环 = ABI 头文件全量 + 每类接口至少 spike 一次 + 可玩切片跑通 5 分钟 —— 稍慢，但真正兑现「可扩展基座」。
- **推荐**：**C**。DOD 写成一份可勾选的清单（见 §3 遗漏项第 2 条），逐项验收。

#### Q2. 「不着急上手玩」意味着基座可以薄到哪一步？
- **为什么重要**：这句话决定了阶段 0 该把精力投在「接口设计」还是「体验打磨」。它是「基座可以更薄」的直接授权，但也藏着一个误读风险（见 R5）。
- **选项与取舍**：
  - A. 薄到「能编译 + ABI 头文件 + 一个测试 ROM 出画面出声」—— UI 可以是 debug 占位。
  - B. 薄到「能玩但 UI 粗糙」—— 把触屏/音频基本调顺。
  - C. 不薄，基座就要基本好用。
- **推荐**：**A 与 B 之间、偏 A**，但必须叠加 Q1 的「5 分钟不爆音不撕裂」时序验收。也就是：**功能薄、验收不薄**。

#### Q3. C ABI 的完备度：全量定义 vs 用多少定义多少？
- **为什么重要**：这是「可扩展基座」的真正兑现点，也是阶段 1/2/3 的公共前置。ABI 后补 = 每个阶段都要回头改壳、改 JNI、改 Kotlin/Java 边界，返工成本最高。
- **选项与取舍**：
  - A. 阶段 0 一次性定义全部接口（含 cheat/patch/memory/save-slot/battery/FDS/NSF 占位），壳只接线用到的子集。
  - B. 用多少定义多少，随阶段增量加。
- **推荐**：**A**（接口头文件全量 + 未实现返回 not-implemented）。实现层只做用到的；接口层一次到位。（具体 ABI 形态由 architect 定，这里定的是「完备度策略」这个产品决策。）

#### Q4. 阶段 1「完整可玩」与阶段 2「魔改」的边界：金手指、IPS/BPS 补丁、存档编辑到底归哪边？
- **为什么重要**：现路线把「金手指」同时塞进阶段 1（完整可玩）和阶段 2（作弊码增强），把「IPS/BPS 补丁」放进阶段 1，但这些本质都是「魔改」系能力。边界不清 → 阶段 1 无限膨胀、永远「快好了」。
- **选项与取舍**：
  - A. 金手指、补丁整体进阶段 2（阶段 1 只做即时/电池存档）。
  - B. 基础金手指（Game Genie / Pro Action Rocky 码表输入）进阶段 1，IPS/BPS 补丁、存档/内存编辑进阶段 2。
  - C. 维持现状（金手指 + 补丁都在阶段 1）。
- **推荐**：**B**。理由：金手指是「可玩性」刚需且 NestopiaUE 内核几乎免费支持，属阶段 1 合理范围；IPS/BPS 是「改 ROM」系、本质是魔改，延后到阶段 2，避免阶段 1 被拖垮。

#### Q5. 用户 ROM 的加载路径（SAF / 文档选择器）进不进基座？
- **为什么重要**：内置 homebrew 只是示例，最终要玩用户自己的 ROM（否则金手指/补丁/存档对谁生效？）。但 SAF 权限、目录扫描、最近列表是一块不小的 UX 工作，且决定「离线/无权限」体验。
- **选项与取舍**：
  - A. 基座只读 assets 内置 ROM，阶段 1 再做 SAF 文件选择。
  - B. 基座就做最小「打开一个 .nes 文件」入口。
  - C. 基座做完整 ROM 库（扫描/最近/缩略图）。
- **推荐**：**A**。基座用 assets + 一个最小「打开文件」入口验证「外部 ROM 进 load()」这条链路即可，完整 ROM 管理库放阶段 1。（SAF 的具体 API 选择由 mobile-perf 评估。）

#### Q6. 「上架」到底是一个里程碑，还是一条持续合规轨道？目标商店是哪个？
- **为什么重要**：上架不是写代码的阶段，是合规+运营；它被塞进阶段 3 会导致 GPL 边界决策被无限拖延，而 GPL 边界反过来决定「能不能闭源/商用」，这是基座阶段就该定的方向性问题。
- **选项与取舍**：
  - A. 明确目标 = Google Play（承担 GPL 源码提供、IARC 分级、模拟器类别政策）。
  - B. F-Droid / itch.io（更宽松，但触达与更新机制不同）。
  - C. 不上架、仅自用/侧载分发。
- **推荐**：**先定「自用分发 + 预留上架」双轨**，并把 GPL 边界决策 + homebrew license 清点提前到「基座结束时」完成（与 compliance t5 对齐）。上架本身降格为一条随时可启动的合规轨道，而不是功能阶段的终点。

#### Q7. 鸿蒙/iOS 移植是近期目标还是远期愿景？要不要在基座阶段做一次「second-shell spike」验证「只换壳」？
- **为什么重要**：「核心不动、只换壳」是全项目最强、也最脆弱的架构假设。等到阶段 3 才发现 C ABI 泄漏了 Android 概念（如某处直接用了 Java 对象、ANativeWindow、Android 音频 API），返工成本最高。
- **选项与取舍**：
  - A. 基座阶段就用一个「第二消费者」把同一 C ABI 编译并跑通（最便宜的是桌面 SDL 壳，或一个最小 ArkTS/空壳），作为 spike。
  - B. 只靠设计评审保证，不做 spike。
  - C. 移植纯远期，基座零投入。
- **推荐**：**A**。一个桌面 SDL 壳成本极低，却能立刻暴露 ABI 的平台泄漏；这是把阶段 3 的风险前移的最划算动作。

### P1 —— 影响阶段 1/2 的顺序与范围

#### Q8. 内置 homebrew 示例选哪些？（附候选清单与选择原则）
- **为什么重要**：内置 ROM 是「可玩」的载体、功能演示的载体，也是包体与合规的一部分——**license 必须允许随 App 再分发**，否则上架即违规。
- **选择原则**（建议）：
  1. 优先「开源仓库里明确写 LICENSE」的（可机器核查）；
  2. 覆盖不同功能面：平台动作 / 射击 / 益智各至少一个，最好有一个较大 CHR 或特殊 mapper；
  3. 体积小（NES ROM 多为 32–512KB，包体几乎可忽略）；
  4. 电池存档不强求（见 Q9）。
- **候选清单**（license 最终由 compliance t5 逐个清点）：

  | ROM | 作者 | 类型 | license 线索 | 备注 |
  |---|---|---|---|---|
  | From Below | Matt Hughson | 下落消除 | MIT（GitHub mhughson） | 2020 年作品，开源明确，现代手感 |
  | Super Sunny World | Matt Hughson | 平台 | MIT（GitHub） | 同源 license，便于统一清点 |
  | Streemerz | Infinite NES Lives | 平台动作 | 开源（GitHub） | 需确认具体条款 |
  | Lan Master | Shiru | 益智 | **CC0**（NESDev 论坛证实） | 再分发最干净 |
  | Lawn Mower | Shiru | 竞速/收集 | **CC0** | 同上 |
  | Alter Ego | Shiru（移植 RetroSouls） | 平台解谜 | 需单列确认 | 非 Shiru 原创，移植权属复杂 |
  | Blade Buster | HLC! | 竖屏射击 | freeware（需确认再分发） | 高表现力、验证高速滚动 |
  | Nomolos: Storming the Castle | Gradual Games | 平台 | 免费下载（需确认） | 较完整、较大 |

- **推荐**：**以 CC0/MIT 的 4–6 个为默认**：From Below、Super Sunny World、Lan Master、Lawn Mower、（Streemerz 若 license 确认）。Alter Ego 和 Blade Buster 作为「license 若能谈妥」的加分项，绝不作为上架前置。**把 license 清点作为上架门禁之一，而不是事后补救。**

#### Q9. 电池存档（SRAM）与即时存档的演示与优先级如何排？
- **为什么重要**：两者独立。电池存档是「游戏本体体验」（更本质），即时存档是 QoL（更通用）。且**可内置的免费 homebrew 大多是无电池存档的街机式游戏**，找不到合适的 SRAM 演示载体。
- **选项与取舍**：
  - A. 电池存档优先、即时存档次之。
  - B. 即时存档优先（任何 ROM 都能演示）。
  - C. 并行做全。
- **推荐**：**A 的接口 + B 的演示**。即：电池存档接口在基座就位、阶段 1 用测试 ROM 验证 SRAM 读写正确性；面向用户的「进度保存」演示用即时存档兜底（因为它对任何内置 homebrew 都成立）。

#### Q10. FDS（磁碟机）与 NSF（音乐）是否从阶段 1 裁剪掉？
- **为什么重要**：FDS 需要 FDS BIOS（任天堂版权、不可再分发，只能用户自备）；NSF 是音乐播放、非「玩游戏」核心。两者都会拖慢阶段 1 的「完整可玩」。
- **选项与取舍**：
  - A. 阶段 1 全裁剪，C ABI 留占位，实现延后。
  - B. FDS 保留（用户自备 BIOS）、NSF 裁剪。
  - C. 全保留。
- **推荐**：**A**。ABI 预留、实现延后；避免阶段 1 被非核心功能拖垮。FDS/NSF 若要上架，需额外澄清 BIOS 来源与内容合规（交 compliance）。

#### Q11. 「减少手搓轮子」与「自定 C ABI + 自写 Java 壳」的张力：是否考虑复用 libretro ABI / 现有 Android 前端？
- **为什么重要**：用户既要「能用开源就用、少造轮子」，又选了自定 C ABI + 自写 Java 壳。libretro 是现成的可移植 C ABI（NestopiaUE 已有 libretro 核），复用能换来整个生态（现成前端、周边工具、社区），但会引入外部依赖和它的抽象约束。
- **选项与取舍**：
  - A. 自定轻量 C ABI（完全可控、贴合本项目、无历史包袱）。
  - B. 直接套 libretro（最快基座、生态最大，但受其 ABI 设计约束）。
  - C. 自定，但设计时对标 libretro 的抽象经验。
- **推荐**：**C**（技术终判归 architect）。产品上：若「最快基座」是硬约束，应认真评估直接吃 libretro 核；若追求「干净可控 + 教学/自研价值」，则自定但对照 libretro 避免重复踩坑。

#### Q12. 外部手柄是阶段 1 的硬需求吗？
- **为什么重要**：飞机场景 + 蓝牙手柄是真实需求，但依赖输入抽象；触屏先行、手柄可后置。
- **选项与取舍**：
  - A. 阶段 1 做蓝牙手柄映射。
  - B. 延后到阶段 1.5。
  - C. 砍掉。
- **推荐**：**B**。C ABI 的 input 抽象（统一的按键位掩码/事件）在基座就位；Android 蓝牙手柄的具体映射放阶段 1.5，不让它卡住「完整可玩」。

#### Q13. 测试 / CI 与性能验收基线何时就位？
- **为什么重要**：这是现路线最大的工程遗漏（见 §3 第 2 条）。基座若没有「回归测试 ROM + CI 自动编 APK + 帧率/功耗基线」，后期魔改与移植就没有安全网。
- **选项与取舍**：
  - A. 基座阶段就位最小集（core 单测 + C ABI 边界测试 + CI 编译 + 一个固定黄金 ROM 的截图/哈希回归）。
  - B. 阶段 1 再补。
  - C. 不上 CI。
- **推荐**：**A**（最小集即可，不追求覆盖率，追求「改坏了能第一时间知道」）。

### P2 —— 体验与产品形态细节

#### Q14. 存档管理有产品形态吗？（多槽位、导出到文件、防丢失）
- **为什么重要**：现路线阶段 1 只写了「存档」两字。飞机上玩，玩家最痛的是「存了又丢」。多槽位、导出/导入存档文件、升级不丢档（存档格式向前兼容）都该在阶段 1 定义。
- **推荐**：阶段 1 至少含「多槽位 + 导出/导入到文件」；存档格式版本承诺在基座就位（见 §3 第 12 条）。

#### Q15. 「魔改」里的调试器 / 内存编辑器是给谁用的——有没有真实用户？
- **为什么重要**：普通玩家不需要调试器、内存编辑器；这可能是「开发者自嗨」功能。若没有真实用户与场景，阶段 2 的这块投入产出比很低，应裁剪或降级为「开发者工具（自用、不随 App 发布）」。
- **推荐**：先验证「谁在什么场景下用」；若答案不明确，把调试器/内存编辑器降为开发者私有工具，阶段 2 只面向玩家的金手指增强 + 补丁 + 存档编辑。

#### Q16. 量化目标有没有 DOD？（包体、最低机型、60fps、功耗）
- **为什么重要**：「高性能低功耗」是约束但没量化。没有「最低支持机型 + 60fps + 待机/游玩功耗 + 包体上限」，性能验收就无法判定。
- **推荐**：在基座阶段写出量化基线（如：中端机稳定 60fps、包体 ≤ X MB、后台/息屏自动暂停省电），作为阶段 1 的验收门禁。（具体数值与 mobile-perf 对齐。）

#### Q17. 「上架后不内置商业 ROM」的边界，用户如何被引导？
- **为什么重要**：App 定位「不内置不下载商业 ROM」，但用户会装商业 ROM。需要一个清晰的引导（「请仅加载你合法拥有的 ROM」）与 ROM 头信息展示，既是合规姿态也是用户体验。
- **推荐**：阶段 1 加入 ROM 头信息展示 + 加载前合规提示文案；与 compliance t5 联动。

## 2. 该领域主要风险与修正建议

| # | 风险 | 后果 | 修正 |
|---|---|---|---|
| R1 | 「基座」被「可玩」绑架，精力花在 UI/音频打磨，ABI 不完整 | 后期每阶段回头改壳、改 JNI | DOD 定为「接口完备 + 每类 spike + 5 分钟时序验收」（Q1） |
| R2 | 阶段边界漂移（金手指/补丁归位不清） | 阶段 1 无限膨胀 | 每功能明确「阶段 / 验收标准 / 依赖」，砍可延后的（Q4） |
| R3 | 「只换壳」假设未经验证 | 阶段 3 移植才发现 ABI 泄漏平台概念 | 基座阶段做 second-shell spike（Q7） |
| R4 | 上架/GPL 决策拖延到阶段 3 | 「闭源/商用」根本方向悬而未决 | GPL 边界 + homebrew license 清点提前到基座结束（Q6，交 t5） |
| R5 | 「不着急上手玩」被误读为「不做时序/渲染验收」 | 交付后才发现渲染格式/音频同步选错 | 区分「产品验收」与「架构验收」，架构验收必须真玩（Q1/Q2） |
| R6 | 内置 homebrew license 未清点就上架 | 上架即合规风险 | CC0/MIT 优先 + 逐个清点 + 上架门禁（Q8，交 t5） |
| R7 | 调试器/内存编辑器属「开发者自嗨」 | 投入产出低、拖慢阶段 2 | 先验证真实用户，否则降级为私有工具（Q15） |

## 3. 路线中遗漏的东西

1. **ROM 加载与管理 UX**：SAF、目录扫描、最近列表、ROM 头识别缩略图——路线通篇没提，但这是「可玩」的核心体验之一。
2. **测试 / CI / 回归基线**：没有安全网，是最大工程遗漏（对应 Q13）。
3. **存档管理与防丢失**：多槽位、导出/导入、升级不丢档——阶段 1 只写了「存档」两字（对应 Q14）。
4. **设置项清单与默认值**：显示比例、控制器映射、连发、滤镜——哪些可配、默认值是什么，未界定。
5. **崩溃日志与本地诊断**：离线无网，本地日志对排障尤其重要（飞机上无法远程）。
6. **性能 / 包体 / 机型量化基线**：把「高性能低功耗」落成可验收数值（对应 Q16）。
7. **签名 / 发布 / 多渠道 / 版本策略**：release 工程化（签名、混淆、版本号策略）通篇缺失。
8. **商店物料与合规里程碑**：隐私政策、IARC 分级、模拟器类别政策、GPL 源码提供页——应作为独立轨道列入（对应 Q6）。
9. **无障碍与输入设备兼容清单**：iOS 的 MFi、鸿蒙的手柄 API 差异，应在移植前置条件里列出。
10. **文档 / ADR / README**：架构决策记录，支撑长期维护与移植交接。
11. **「魔改」的合法边界引导**：用户自有 ROM 打补丁 vs 分发改版 ROM 的边界提示（与 compliance t5 联动）。
12. **存档格式/版本的向前兼容承诺**：升级 App 不丢档，阶段 1 就该定为硬承诺。
