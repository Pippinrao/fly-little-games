# t5 合规与许可证评估：GPLv2 与 homebrew 再分发

> 领域：许可证与合规（NestopiaUE/GPLv2、闭源上架边界、homebrew 再分发、魔改版权风险）
> 评估人：compliance ｜ 日期：评估时点
> 内核前提：NestopiaUE 为 **GPLv2**（[SourceForge](https://sourceforge.net/projects/nestopiaue/)、[Wikipedia](https://en.wikipedia.org/wiki/Nestopia)）；备选内核 **ares** 现为 **ISC**（permissive，[ares GitHub](https://github.com/ares-emulator/ares)、[Emulation General Wiki](https://emulation.gametechwiki.com/index.php/Ares)），但其历史许可曾为 CC BY-NC-ND，需按所用快照核验。

---

## 0. 一句话结论（TL;DR）

1. **JNI 链接（无论静态还是动态 .so）都会把 Java 壳和整个 App 变成 GPLv2 的“结合作品”**——.so 规避不了 GPL。想闭源只有两条干净路：**换 permissive 内核（ares/ISC）** 或 **进程隔离（法律仍灰色、移动端代价高）**。
2. **GPLv2 不禁止商业上架**：可上 Google Play、可收费/接广告/内购，前提是履行源码公开、署名、不得附加额外限制。RetroArch（GPLv3）就是 Play 上 GPL 模拟器的先例。
3. **homebrew “免费下载” ≠ “允许再分发”**：内置进 App 就是你对外分发，必须逐条拿到明确授权，且要避开含任天堂素材、NC（非商用）许可的 ROM。
4. **魔改边界**：只做“工具/能力”，绝不内置或分发商业游戏的补丁、改版 ROM、作弊码数据库；FDS 需任天堂 BIOS，必须用户自备。

## 1. 按优先级排序的尖锐问题 / 决策点清单

### P0（根决策，先问，决定整个项目的合规形态）

#### Q1. 你要「全开源 GPLv2」还是「闭源/商业化」？——这是所有后续决策的根

- **为什么重要**：NestopiaUE 是 GPLv2 copyleft。只要你对第三方分发（上架、发 APK 给别人），JNI 调用就构成“结合作品”，Java 壳 + C++ 核心必须整体 GPLv2 开源。这条一旦走错，后面所有“闭源上架”“白标”“卖授权”的设想都作废。
- **选项与取舍**：
  - A. **全开源 GPLv2**：App 整体 GPLv2，源码放 GitHub。**仍可收费/上架/接广告/内购**（GPL 不禁止商业），只是购买者有权再分发（这实质封顶了“卖拷贝”的商业模式，但不影响广告/IAP/捐赠）。零法律争议、成本最低。
  - B. **闭源/商业化**：必须换 permissive 内核或做进程隔离（见 Q4）。换内核 = 集成重做、功能面可能缩水；进程隔离 = 架构复杂度 + 性能/内存代价 + 法律仍灰色。
  - C. **“核心开源、壳闭源”**：法律上不成立（壳调用核心 = 结合作品），别走这条路。
- **推荐**：**A（全开源 GPLv2）**。个人/独立模拟器开源不损失商业价值；RetroArch 证明 GPLv3 都能上 Play。把“换 permissive 内核”留作未来的兜底选项（配合 Q2 的抽象层设计），而不是现在就为闭源买单。

#### Q2. 是否接受“将来可能换 ares(ISC)”作为闭源的兜底？

- **为什么重要**：若未来出现硬性闭源需求（被收购、白标、iOS 上架争议），唯一干净方案是换 permissive 内核。这需要阶段0 就把“内核抽象层/适配层”做出来，否则换内核 = 推倒重来。
- **选项与取舍**：
  - A. 继续 NestopiaUE，不预留抽象（省事，但锁死 GPL）。
  - B. 阶段0 定义 core API 抽象 + 可替换适配层，内核实现可插拔（符合“可扩展基座”定位，换内核成本可控，但抽象本身有开发成本）。
  - C. 现在就换 ares(ISC)（可闭源，但 ares 的 NES 功能面/精度/mapper/FDS/金手指/即时存档需 emulator-core 专家验证，可能弱于 NestopiaUE 或需补活；且 ares 历史许可曾为 CC BY-NC-ND，须锁定快照并核验许可）。
- **推荐**：**B**。现在不换内核（NestopiaUE 功能面最全），但阶段0 就把“内核适配层”做成架构第一公民。这样“是否闭源”未来可逆，代价可控。

#### Q3. 上架渠道是什么？（决定义务细节与政策风险）

- **为什么重要**：不同渠道政策不同。Google Play **允许 GPL**（RetroArch 先例），但**禁止从非 Play 渠道下载可执行代码**（dex/jar/so——这正是 RetroArch 1.9.0 被 Play 卡住、砍掉 Core Downloader 的原因）。恰好本项目“完全离线、内置 homebrew、不下载 ROM”与该政策天然一致，是合规加分项，**必须守住“不下载可执行内容”这条线**。
- **选项与取舍**：
  - A. 仅官网/GitHub 分发 APK（自由，用户少）。
  - B. **Google Play + GitHub 源码公开**（主流，合规）。
  - C. F-Droid（要求完全自由软件 + 可复现构建，可作为补充渠道）。
  - D. 鸿蒙/iOS 商店（iOS 对模拟器 + GPL 有独立且更严的政策，见“遗漏项”）。
- **推荐**：**B + 可选 C**。上 Google Play 并同步 GitHub 源码；保持“完全离线、绝不运行时下载 ROM/核心/可执行代码”，规避 Play 政策与 GPL §3 的复杂度。

### P1（影响架构 / 构建 / 内容）

#### Q4. 静态链接 vs 动态 .so vs 进程隔离——`.so` 到底能不能规避 GPL？（用户点名的核心问题）

- **为什么重要**：这是最常见的误解。**GPL 下静态链接与动态链接没有区别**：FSF 明确说“无论静态还是动态链接，都构成结合作品”，且“如果主程序与插件互相函数调用、共享数据结构，就构成单一程序”（[GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#GPLStaticVsDynamic)）。JNI 正是“互相函数调用 + 共享帧缓冲/音频缓冲”的教科书案例。
- **选项与取舍**：
  - A. 静态链接进 .so + Java 壳：整体 GPL。
  - B. 动态 .so + dlopen/JNI：**整体 GPL，与 A 无差别**（.so 只是交付形态，不改变“结合作品”结论）。
  - C. 独立进程 + IPC（Binder/socket/共享内存）：主张 GPLv2 §2 末段“mere aggregation”。但 60fps 帧缓冲 + 音频走共享内存，本身就是“共享数据结构”，会被 FSF 视为单一程序；且移动端进程隔离的内存/延迟/复杂度代价巨大，法律上**无判例背书、仍是灰色**。
- **推荐**：**接受现实——直接静态链接、全开源 GPLv2**。不要为规避 GPL 做进程隔离（收益不确定、成本高）。若真要闭源，换 permissive 内核（Q2）比进程隔离干净得多。

#### Q5. FDS（磁碟机）要支持吗？BIOS 谁提供？

- **为什么重要**：FDS 需要 `disksys.rom`，这是**任天堂版权 BIOS**，NestopiaUE 不内置、需用户自备（[社区教程](https://www.romulation.org/threads/tutorial-so-you-want-to-play-fds-roms-on-a-nes-emulator-but-dont-know-how.29336/)、[RetroPie 文档](https://retropie.org.uk/docs/Famicom-Disk-System/)）。内置或引导下载 = 直接侵权 + 商店违规。
- **选项与取舍**：
  - A. 只提供“用户自备 BIOS 路径”能力（合规）。
  - B. 内置/自动下载 disksys.rom（违法）。
  - C. 基座阶段砍掉 FDS，后续再评估。
- **推荐**：**A**。同时**审计 NestopiaUE 源码，确认无任天堂派生代码**（FDS 处理、调色板等）。FDS 功能可留接口，但 BIOS 一律用户自备。

#### Q6. 内置哪些 homebrew ROM？逐条授权怎么核验？

- **为什么重要**：**“免费下载” ≠ “允许再分发”**。很多 nesdev/itch.io homebrew 免费但明确禁止转载或禁止商用捆绑；内置进 App = 你对外分发该 ROM，必须逐条拿到明确授权。反例：itch.io 某社区帖子明说“QUOD INIT EXIT 才允许再分发，KOG/MeMO 免费但禁分发”（[itch.io 讨论](https://itch.io/t/355507/approval-to-share-your-roms)）。
- **选项与取舍**：
  - A. 只内置**明确 permissive** 的 ROM（CC0 / CC-BY / MIT / ISC / Public Domain，作者在仓库或页面写清 license）→ 带署名 + LICENSE 内置。
  - B. “免费但未声明许可”的 ROM → **一律视为禁止再分发，不内置**。
  - C. 联系作者拿书面授权（适合特定精品 demo）。
- **关键陷阱**：① 部分 homebrew 用了任天堂素材（马里奥/洛克人等）→ 即使作者“免费”，也含任天堂版权，**不能内置**；② CC BY-SA 等 share-alike 对“捆绑”一般只要求署名 + 同许可转发，需逐条细读；③ **NC（非商用）许可**（如 CC BY-NC）在你 App 一旦收费/接广告/上架即违规，一律避开。
- **推荐**：**A**，数量控制在 3–5 个、体积小、能体现功能（存档/金手指/mapper）的 permissive 无任天堂素材 ROM；建立“内置内容清单 + 每项 license 文件 + 署名页”机制，其余靠“用户自备 ROM 加载”能力补齐。

### P2（影响功能范围 / 上架义务）

#### Q7. 金手指数据库（cheat DB）内置吗？

- **为什么重要**：作弊码本身一般是功能性数据、不构成版权表达，但“整理成库”可能含编辑性选择而有自身许可；且内置针对商业游戏的作弊码 DB 属“擦边”。NestopiaUE 自带 cheat 数据库的许可需核查。
- **选项与取舍**：
  - A. 只做“用户手动输入/导入金手指”能力，不内置 DB（最干净）。
  - B. 内置明确 permissive 许可的 cheat DB，并核查来源许可（NestopiaUE 的 DB）。
  - C. 内置覆盖商业游戏的作弊码 DB（有风险，别做）。
- **推荐**：**A**（阶段0/1 只做手动 + 导入）。若要内置 DB，只用明确 permissive 且不针对商业游戏编目的来源，附许可文件。

#### Q8. “魔改游戏 / 金手指 / 补丁”的法律边界画在哪？

- **为什么重要**：风险分层。给用户**自己拥有的 ROM** 打补丁 = 低风险（个人使用语境）；但**分发补丁库 / 改版 ROM** = 很可能侵权。
- **分层（风险从低到高）**：
  - 金手指（运行时改 RAM）：最安全，纯功能。
  - 改存档 / 内存编辑：用户自己的存档，安全。
  - IPS/BPS 补丁：只含差异数据，通常被容忍，但若补丁含原作版权表达（整段资源/反汇编）仍可能构成衍生作品，**分发补丁是灰色**。
  - 分发“打好补丁的商业 ROM”：**明确侵权**。
- **选项与取舍**：
  - A. **工具-only**：只提供“把补丁应用到用户自备 ROM”的能力 + 手动导入，不内置/不链接/不引导下载任何商业游戏补丁。
  - B. 内置商业游戏补丁库 / 改版 ROM（高风险，别做）。
  - C. 提供补丁社区/市场（更高风险）。
- **推荐**：**A**。把“App 只做能力、不做内容分发”写进项目宪法。

#### Q9. 上架后 GPLv2 §3 源码义务怎么履行？

- **为什么重要**：GPLv2 §3 要求分发二进制时提供对应源码（附源码 / 书面要约 3 年 / 或非商业时传他人要约）；§2a 要求保留版权声明；§6 禁止附加额外限制。商店分发触发全部义务。
- **选项与取舍**：
  - A. **GitHub 公开源码 + App 内“Licenses/Source”页附链接**（RetroArch 等广泛采用的务实合规，Play 也要求开源声明页）。
  - B. 严格书面要约（麻烦，易过期）。
  - C. 不提供（违规，会被版权人/商店下架/DMCA）。
- **关键点**：源码须“对应分发版本”且含**构建脚本**（CMakeLists、NDK 配置、对内核的补丁/改动）。换内核/改代码必须同步更新。
- **推荐**：**A**，且从阶段0 就做：GitHub 公开 + CI 可复现构建 + App 内许可页，把合规做进基座，而不是上架前补课。

## 2. 该领域主要风险与修正建议

| # | 风险 | 修正建议 |
|---|------|----------|
| R1 | 把 GPL 当“免费 = 随便用”，只关注内核、忽略内容与依赖 | 建立全链路 LICENSE/NOTICE 体系：内核 + homebrew ROM + cheat DB + 所有第三方库。 |
| R2 | 误以为动态 .so 能规避 GPL，导致“核心 GPL、壳闭源”的错误架构 | 接受“JNI = 结合作品”；要闭源就换 permissive 内核或进程隔离，并尽早定 Q1。 |
| R3 | homebrew 未经授权内置（“反正免费”） | 逐条授权核验 + 内置内容 LICENSE 清单 + 署名页；禁止无许可/NC/含任天堂素材的 ROM。 |
| R4 | FDS disksys.rom 或其他任天堂素材混入分发 | 用户自备 BIOS；审计内核源码无任天堂派生代码。 |
| R5 | 上架时触发 Play 政策（禁从非 Play 下可执行代码、开源声明、政策随版本变化） | 守住“完全离线、不下载任何可执行内容”；开源声明页做进基座。 |
| R6 | **GPLv2 与 GPLv3 许可不兼容**：引入 GPLv3 库进同一 .so 导致许可冲突 | 核查所有 C++ 依赖的许可与版本；GPLv2 兼容 MIT/BSD/zlib/ISC/Apache-2.0，与 GPLv3 代码不能混用（除非整体升 GPLv3）。构建时生成 SBOM（reuse-tool / gradle license report）。 |
| R7 | 商标/品牌侵权：App 名/图标用“NES/红白机/FC/任天堂”标识 | 命名与图标避开任天堂商标；商店标题慎用“NES”。 |
| R8 | 魔改功能被解读为“诱导侵权 / 规避技术措施”（DMCA §1201 及各国反规避条款） | 金手指/补丁针对老卡带无 TPM、风险低，但坚持“工具-only、不分发内容”；iOS 商店对模拟器/作弊功能审核更严，需单独评估。 |

## 3. 路线中遗漏的东西

1. **“合规/许可”没有作为显式横切关注点**。建议把“合规基线”（LICENSE/NOTICE、SBOM、源码公开、App 内许可页）写进阶段0 并贯穿始终，而不是只在阶段3“上架合规”里提一句。
2. **缺少“可替换内核的抽象层”目标**。阶段0 应定义 core API 抽象 + 内核适配层，既是技术解耦，也是未来换 permissive 内核（闭源兜底）的保险——把 Q2 的选项 B 做进架构。
3. **iOS 上架没有单独合规评估**。iOS App Store 对模拟器类 App（可加载外部 ROM/BIOS、作弊功能）有独立且更严政策；**GPL 上 App Store 长期有“App Store 条款 vs GPL §6 不得附加限制”的争议**（VLC 曾因此下架后改许可再上架）。移植 iOS 前须单独做法律/政策评估，可能反过来影响架构（动态库/进程模型/是否换内核）。
4. **FDS/NSF 的 BIOS 与内容来源策略缺失**。FDS 需任天堂 disksys.rom；NSF 是商业音乐版权。需要明确“用户自备 + 不内置不引导下载”。
5. **内置 homebrew ROM 清单的授权审核流程缺失**。谁负责、记录什么、license 文件放哪、如何随版本更新，需要一条流程。
6. **鸿蒙/国内上架的本地合规未覆盖**。华为应用市场政策、国内版权（虽 GPL 判例少但版权仍受保护）、软件著作权登记等。
7. **SBOM / 依赖许可证工具链缺失**。建议引入 `reuse-tool`、gradle license report，把第三方依赖许可做成可审计的清单。
8. **品牌/命名/图标的商标清检缺失**。项目起名与视觉资产阶段就应做商标清检，避免后期改名的沉没成本。
