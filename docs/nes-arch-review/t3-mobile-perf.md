# t3 · Android 渲染 / 音频 / 功耗 / 离线体验评估（mobile-perf）

> 评估对象：安卓单机红白机模拟器（NestopiaUE 内核，C++ 主线 + Java 外壳 + JNI），完全离线、飞机上长时间游玩、高性能低功耗。
> 结论视角：移动性能功耗专家。

---

## 0. 一句话结论

NES 的帧只有 256×240、音频是 60.0988Hz 的"慢速"流，**这台机器在性能上对现代手机毫无压力**——真正的敌人不是算力，而是三件事：**(1) 忙等/连续渲染导致的 CPU 常醒与 GPU 常醒（功耗大头）**、**(2) 音频缓冲与漂移没治理导致的长时爆音（6 小时航班必然发作）**、**(3) 生命周期/存档没处理好导致的"后台白烧电 + 丢进度"（飞机上致命）**。渲染强烈建议走**软件 RGB565 blit + SurfaceView**（不开 GPU），音频以**音频为主时钟 + 阻塞写**，文件用 **assets + SAF(persistable) + 私有目录**，并拒绝 `MANAGE_EXTERNAL_STORAGE`。只要这四条钉死，"高性能低功耗"就自然达成，GPU 滤镜/低延迟音频留到阶段 2 再按需引入。

## 1. 按优先级排序的尖锐问题 / 决策点清单

### P0 —— 决定基座形态，必须先拷问

---

#### Q1. 渲染管线选型：软件 blit vs GLSurfaceView vs 原生 EGL？

**为什么重要**：渲染抽象是基座的"地基"，选错方向意味着要么白开 GPU 上下文常醒烧电，要么阶段 2 想加滤镜时推翻重做。NES 帧只有 256×240，`60fps` 的软件 blit 对 CPU 几乎零开销，**视频上屏本身不是性能问题，GPU 反而是最不该醒的那个**。

**建议选项与取舍**：
- **A. 软件渲染 + `SurfaceView`(`ANativeWindow_lock/unlockAndPost`) 直接 blit RGB565**：零 GL 上下文、零 GPU 唤醒、最省电；NEON 加速后 60fps 缩放+上屏几乎无感。缺点：没有 shader 滤镜、任意旋转/缩放要 CPU 或 View 层做。
- **B. `GLSurfaceView` + 纹理上传**：最省事、现成 GL 线程与 EGL 生命周期；但每帧 `glTexSubImage2D` 上传会唤醒 GPU、多一次拷贝；且必须设 `RENDERMODE_WHEN_DIRTY`，否则默认连续渲染=GPU 常醒。好处是阶段 2 滤镜顺手。
- **C. `TextureView`/`SurfaceTexture`**：GL 输出进 View 树可做合成/动画，但多一跳拷贝+延迟，NES 场景没必要。
- **D. 原生 EGL + 自定义 GL 线程**：完全可控、可做扫描线/CRT/任意缩放，但手搓生命周期/上下文重建成本高。

**推荐**：**A（软件 RGB565 + SurfaceView）**，但把"渲染器"抽象成接口（native 拿到一块目标缓冲 + 目标尺寸，由 `SoftwareBlitter` 实现；未来 `GLRenderer` 作为另一实现注入）。内部帧缓冲保留 RGB888 供将来滤镜，上屏前量化到 RGB565（2 字节/像素，省一半带宽/内存，NES 原生 12bit 色域下视觉差异可忽略）。**理由**：NES 场景软件渲染最省电、最简单、最稳；GPU 滤镜是阶段 2 增值项，别让它阻塞基座。

---

#### Q2. 主时钟与帧同步 / 省电架构：忙等 vs 阻塞？音频 vs vsync 谁做主？

**为什么重要**：这是**全项目最大的功耗杠杆**。错误示范 `while(running){runFrame();}` 忙等会让 CPU 满载、发热、掉电；正确做法是阻塞式循环，让 CPU 在帧间进入 idle/deep-sleep。它同时决定模拟线程长什么样，也是"省电"这条硬约束的直接落点。

**建议选项与取舍**：
- **A. 音频为主时钟**：native 循环 `runFrame → 写音频 → write() 缓冲满时阻塞`，天然按 60.0988Hz 精确步进、零漂移、CPU 阻塞睡眠；视频侧"取最近完成帧"上屏。最简单、最省电、音频永不爆音。缺点：上屏时机不完全对齐 vsync，可能有轻微 tearing。
- **B. vsync 为主时钟**（`AChoreographer`/`Choreographer` 回调）：每帧对齐显示、视频最顺；但 60.0988 vs 60.00 的漂移要靠音频缓冲吸收，需漂移补偿/动态重采样，复杂。
- **C. 混合**：音频定速 + vsync 限流上屏（模拟由音频驱动，上屏由 vsync 触发）。

**推荐**：基座用 **A**（音频主时钟 + 阻塞写），"最近完成帧"通过原子指针/双缓冲交给渲染线程，渲染线程用 `AChoreographer`(API24+) 只在 vsync 时上屏避免 tearing。**绝对禁止忙等**：一切等待都用阻塞原语（`AudioTrack.write`、`AChoreographer` await、condvar/eventfd）。理由：把漂移问题从"复杂工程"降为"不存在"，同时最大化帧间睡眠。

---

#### Q3. 音频管线选型：Java AudioTrack vs Oboe/AAudio？缓冲与采样率？

**为什么重要**：决定爆音/延迟/功耗/依赖四条线。NES 不是节奏游戏，对延迟不敏感（<200ms 无感），但**爆音会让长时游玩体验崩溃**；同时音频 buffer 是主时钟的载体，缓冲策略直接决定功耗与稳定性。采样率选错会造成双重重采样浪费 CPU/损音质。

**建议选项与取舍**：
- **A. Java `AudioTrack` 流式**：最简单够用；每次 write 有 JNI 边界、缓冲粒度粗，但配合阻塞写已能当主时钟。
- **B. 原生 `AAudio`/OpenSL ES**：native 侧直接写避免 Java 往返；OpenSL ES 已弃用但兼容最广。
- **C. Oboe（AAudio API27+ / OpenSL ES 回退）**：官方推荐，低延迟 + MMAP fast path 减少 CPU 唤醒（更省电），`AAUDIO_USAGE_GAME` 标记；MIT 许可。成本：多一个 C++ 依赖 + API26 以下走 OpenSL。
- **D. 直接 AAudio（API26+）**：最低延迟，但要自己处理设备能力差异。

采样率：NestopiaUE 原生约 44.1kHz，Android 混音多设备原生 48kHz。**只做一次重采样**：要么 emu 直接输出 48k，要么 44.1k 交给 Oboe 的高质量 SRC 转到设备 rate（官方文档明确推荐这两条路径之一）。

**推荐**：**基座用 A（Java AudioTrack，缓冲 2~4 帧 = 33~66ms，write 阻塞做背压）**先把闭环跑通；**阶段 1 切 C（Oboe，`AAUDIO_USAGE_GAME`，48k 输出或 Oboe SRC）**，换取低延迟 + fast path 省电 + 原生侧无 Java 往返。接口按"音频输出 sink"抽象，替换无痛。**红线**：缓冲不要 <1 帧（连爆）也不要 >100ms（漂移/延迟感知），并处理 underflow 回调触发"重新预填/短暂静音"而非死锁。

---

#### Q4. 文件访问与离线：ROM 从哪来、存档写哪、用什么权限？

**为什么重要**：完全离线 + 飞机上不能联网授权/装东西，决定用户 ROM 和存档怎么存、重启后能否无缝续玩；权限选错会在阶段 3 卡 Google Play 上架或被拒。

**建议选项与取舍**：
- **A. 内置 homebrew 放 `assets`**：零权限、真离线、随包分发；只读，需拷贝到 native 缓冲加载。适合示例 ROM。
- **B. 用户 ROM 走 SAF（`ACTION_OPEN_DOCUMENT` + `takePersistableUriPermission`）**：无需存储权限、Play 友好、跨重启有效；但每次读 URI 慢/受 provider 限制，首次导入后应复制到私有目录缓存。
- **C. `MANAGE_EXTERNAL_STORAGE`/`READ_EXTERNAL_STORAGE`**：扫目录方便，但 MANAGE 是 Play 强管控权限，上架必被审查；Android 11+ 分区存储进一步收紧。
- **D. 存档写 app 私有目录 `getFilesDir()`**：无权限、可靠、离线；但换机/清数据会丢，需导出功能（SAF 写）。

**推荐**：**A + B + D**（assets 内置 homebrew + SAF persistable 导入缓存 + 存档写私有目录，阶段 1 加导出/导入）。**明确不申请 `MANAGE_EXTERNAL_STORAGE`**。理由：这是唯一"离线 + 上架合规 + 可再分发"的组合。

### P1 —— 决定体验与稳定性

---

#### Q5. 生命周期 / 后台 / 息屏 / 自动存档：怎么处理？

**为什么重要**：飞机上用户随时按电源键、接电话、切 app、崩溃；模拟器不自动停会继续烧 CPU；丢进度 = 灾难。这是省电与数据安全的最大单点。

**建议选项与取舍**：`onPause`/`onStop` 时自动：暂停模拟 → 写自动即时存档槽 + flush 电池 SRAM → `AudioTrack.pause/stop` → 释放 surface → **停止模拟线程（不是 idle 循环）**；`onResume` 恢复。可选"崩溃/进程被杀恢复"：检测上次异常退出，提示恢复自动存档。

**推荐**：**阶段 0 就要有"pause 即停线程 + 存档"**（即使自动存档槽是阶段 1 功能，也要在基座留好钩子），作为基座验收项。理由：实现成本低、收益极大，不能拖。

---

#### Q6. minSdk / ABI / 目标设备：定多少？

**为什么重要**：minSdk 决定能否用 `AChoreographer`(24)/`AAudio`(26) 的现代 API，还是必须写 OpenSL/Java Choreographer 回退；ABI 决定包体与覆盖。

**建议选项与取舍**：
- minSdk：21（Android 5）覆盖最广但要两套音频/时钟回退；24 可用原生 vsync；26 可用 AAudio。Play 主流最低 21+，个人侧载想支持旧平板需权衡。
- ABI：`arm64-v8a`（现代全部）+ `x86_64`（Windows 模拟器测试）；`armeabi-v7a`（2015 前 32 位）基本可砍，Play 已强制 64 位。

**推荐**：**minSdk 24**（换取原生 vsync + 更简单时钟），**ABI 出 arm64-v8a + x86_64**（x86_64 仅开发期用，上架时 App Bundle/渠道切分掉）。若明确要覆盖上古 32 位设备，再考虑 v7a + minSdk21，但要预算"OpenSL 回退 + Java Choreographer 回退"两套代码。理由：NES 目标设备就是现代手机/平板，24 已覆盖 2016 年后 95%+ 设备。

---

#### Q7. 长时间运行的漂移与爆音治理？

**为什么重要**：60.0988Hz ≠ 60Hz，6 小时航班累计漂移可观；无治理 → 音频 buffer 越界/爆音或视频撕裂。低端机掉速/发热降频也会 underrun。

**建议选项与取舍**：音频主时钟（Q2 方案 A/C）天然免疫漂移，无需处理；若 vsync 主时钟则需漂移补偿（每 N 帧插/删 1 采样）或 Oboe SRC 动态重采样。另加 **auto frame skip**：负载过高时优先跳视频帧保音频不爆音。

**推荐**：主时钟用音频（把漂移降为不存在）+ "掉帧保音频"策略 + thermal 降频下的缓冲弹性。这是长时稳定性的保险。

---

#### Q8. JNI 边界与内存策略：怎么切？

**为什么重要**：高频 JNI（每帧每像素）吃 CPU/电量、触发 GC 抖动卡顿；长时 native 泄漏会让 6 小时航班后 OOM/卡死。

**建议选项与取舍**：每帧一次 `runFrame()` 返回结果结构；帧/音频缓冲用 persistent `DirectByteBuffer`（native 持有、Java 不拷贝）；避免 `GetByteArrayElements` 每帧 copy；输入用 1 字节位掩码；native 对象显式 release（不依赖 finalizer）；Java 侧避免每帧分配对象。

**推荐**：阶段 0 钉死"**每帧一个 JNI 调用 + 预分配直接缓冲 + 显式生命周期**"三条铁律，并配 1 小时跑机泄漏/GC 压测作为基座验收项。理由：这是"高性能低功耗"的直接落地，也是移植 iOS/鸿蒙时 C ABI 的天然预演。

### P2 —— 后置增强

---

#### Q9. GPU 滤镜 / 整数缩放：什么时候做？

**为什么重要**：扫描线/CRT 滤镜是模拟器"手感"核心卖点之一（要 GPU shader）；整数缩放（2x/3x/4x nearest）保像素。做在软件层 vs GPU 层决定是否值得引入 GL。

**推荐**：阶段 0 只做软件 nearest 整数缩放（无滤镜）；阶段 2 引入 GL 渲染器实现做 CRT/扫描线，接口在阶段 0 预留（Q1 已预留 renderer 抽象）。别为滤镜提前开 GPU。

---

#### Q10. NSF 音乐播放模式的省电？

**为什么重要**：NSF 是纯音频无画面；按游戏模式跑，屏幕常亮白烧电。飞机上"听音乐"场景希望关屏/降亮度继续播。

**推荐**：阶段 1/2 加 NSF 播放器模式并支持"无视频渲染 + 关屏播放"（复用音频主时钟架构，天然支持，还顺便验证"渲染与音频解耦"的架构正确性）。低成本省电亮点。

---

#### Q11. 蓝牙耳机 / 音频焦点？

**为什么重要**：飞机上多用蓝牙耳机，BT 链路额外 100~300ms 延迟（NES 无感）；但音频焦点被抢（来电/其他 app）需正确 pause；BT 采样率/通道可能不同触发重采样。

**推荐**：阶段 1 加音频焦点处理（失焦即暂停模拟，结合 Q5），BT 延迟不做补偿（过度工程），BT 采样率交给 AudioTrack/AAudio 系统重采样。焦点是稳定性问题，补偿不是。

---

#### Q12. 功耗验收指标与性能基准？

**为什么重要**："高性能低功耗"没有量化指标就无法验证、无法回归；飞机 6~8 小时是硬需求。

**推荐**：阶段 0 落地基准 ROM + Perfetto 抓帧时间/CPU 曲线，定义验收（如参考设备运行压力 homebrew 60fps 时 CPU <15% 单核、亮屏连续游玩 ≥6h），选 1~2 个"压力 homebrew"做回归。没有基准的"优化"会在阶段 2 失控。

## 2. 主要风险与修正建议

| # | 风险 | 修正建议 |
|---|------|----------|
| 1 | 忙等/无阻塞循环 → CPU 满载发热掉电 | 音频阻塞主时钟 + 禁忙等（代码审查红线） |
| 2 | 音频缓冲不当 → 长时爆音/漂移 | 2~4 帧缓冲 + underflow 恢复 + 音频主时钟 |
| 3 | GLSurfaceView 默认连续渲染 → GPU 常醒 | 直接软件 blit；若用 GL 必设 `RENDERMODE_WHEN_DIRTY` |
| 4 | 生命周期不处理 → 后台白烧电 + 丢进度 | pause 即停线程 + 自动存档 + 释放 surface/audio |
| 5 | 权限选错（`MANAGE_EXTERNAL_STORAGE`）→ 上架被拒 | SAF + persistable + 私有目录，不申请 MANAGE |
| 6 | JNI 高频/每帧分配 → GC 抖动 + 耗电 | 每帧一调 + 直接缓冲 + 显式生命周期 |
| 7 | 长时 native 内存泄漏 → 6 小时航班 OOM | 1 小时跑机压测 + LeakCanary/native heap 回归 |
| 8 | 采样率双重重采样 → CPU/音质浪费 | 单次重采样（48k 输出 或 Oboe SRC） |
| 9 | 120Hz/高刷屏 vs 60.0988 不匹配 → 抖动/撕裂 | vsync 限流上屏 + 音频定速；可选 `Surface.setFrameRate`(API30) |
| 10 | 热降频 underrun → 掉帧/爆音 | auto frame skip 保音频 + 缓冲弹性 |
| 11 | 第三方音频库（Oboe 等）静态链进 GPL core 的许可争议 | 动态链接/隔离，交 compliance 定论 |

## 3. 路线中遗漏的东西

1. **生命周期自动存档与崩溃/进程被杀恢复**——路线只写了"存档"，没写"pause 即自动存档 + 异常退出恢复"，这是飞机场景数据安全第一优先级。
2. **量化功耗/性能验收指标 + 基准 ROM/压测**——"高性能低功耗"没有验收标准（Q12）。
3. **NSF 无渲染/关屏播放省电模式**——纯音频场景的省电亮点（Q10）。
4. **音频焦点 + 来电/蓝牙耳机场景**——稳定性问题，路线未提（Q11）。
5. **长时漂移/爆音治理 + auto frame skip**——路线只有"声音"，没有"音频稳定性治理"这条工程线（Q7）。
6. **surface 生命周期**：Home 键、来电、分屏/多窗口、旋转导致的 **EGL 上下文丢失与 surface 重建/resize** 未提。
7. **进程被杀/Activity 重建的状态恢复**（`onSaveInstanceState` + native 状态快照）。
8. **高刷屏（90/120Hz）帧率策略** 与 `Surface.setFrameRate`(API30) 可选优化。
9. **输入路径的延迟与省电平衡**：触屏轮询频率、外接手柄（USB/蓝牙）的接入与功耗。
10. **离线冷启动路径自测**：设备重启后从 SAF persistable URI 恢复 ROM 列表、assets 加载、无网络环境的完整回归。
11. **电池/低电量/Doze/App Standby 交互**：正确用 `FLAG_KEEP_SCREEN_ON`、不申请多余后台权限、省电模式下的前台豁免验证。
12. **包体/签名/离线侧载分发与版本升级路径**——飞机上无法更新，侧载安装与离线升级策略未提。
13. **FDS 磁盘换面 / NSF 播放** 在渲染-音频管线里的特殊路径（与 emulator-core 交接，但渲染/音频侧要预留"无 surface"状态）。
