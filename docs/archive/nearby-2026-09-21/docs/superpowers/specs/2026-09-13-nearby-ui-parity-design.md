## 3. 大厅的最小增量

### 3.1 状态入口

| 状态 | 右上角中文 | 点击目标 | 开始游戏规则 |
|---|---|---|---|
| 无认证连接 | 附近联机 | 联机首页 | 按现有单人行为 |
| 请求/认证/建网中 | 附近联机 | 当前进行中的步骤 | 不自动开始或替换单人游戏 |
| 双方身份、通道及兼容性检查完成 | 双人联机中 | 连接概览，显示已验证好友和断开入口 | 选游戏后进入本局确认 |
| 已建立的连接中断 | 联机中断 | 重连状态与可执行操作 | 不静默转单人；禁用双人开局 |
| 用户明确断开/原连接确认终止 | 附近联机 | 联机首页 | 恢复单人行为 |

扫码成功、房主接受、输入正确配对码、单端 SAS 确认，均不足以显示“双人联机中”。应用后台恢复时先读取真实 session，不从持久化布尔值恢复“已连接”。

### 3.2 两组筛选叠加

独立状态：`category`、`query`、`multiplayerOnly`、每类 `selectedCanonicalId`、连接状态。

```text
visible = existingCategoryAndSearch(catalog, category, query)
if multiplayerOnly:
    visible = stableFilter(visible, game.multiplayerEligibility == SUPPORTED)
reconcileSelection(visible)  // 保留现有每类选择与回退规则
```

- 首次使用 `multiplayerOnly=false`；用户修改后作为本机大厅偏好保存，重启后恢复。连接、断开、返回大厅、换分类均不改变它。
- 分类与搜索沿用当前规范化、去重、收藏、近期顺序和 ALL 热度排序；支持双人过滤不重新排序，不以名称猜测能力。
- `SUPPORTED / UNSUPPORTED / UNKNOWN` 为三值能力。UNKNOWN 显示“支持情况待确认”，开关打开时不计入结果；它不等于“不支持”。能力判断须来自共享、版本化的游戏配置，不能从文件名、P2 字样或手柄数量推断。
- SUPPORTED 表示游戏可提供已验证的双人玩法，不代表任意两台设备组合已通过硬件门禁。两端能力与资源检查在本局准备时再次执行。
- 例：“收藏 + 支持双人”只保留收藏中的 SUPPORTED；关闭开关仍在收藏。内置零结果不得跳回全部；显示当前分类与“关闭支持双人筛选”动作。
- 双人状态下关闭开关仍可浏览单人游戏；左侧启动按钮显示具体不可用原因，不擅自断开朋友，不自动启动单人。
- “双人联机开始”只提交当前游戏提议并进入本局配置，不绕过双方确认。单人“开始游戏”保持原路径。

### 4.1 两种加入入口

```text
创建联机 → 展示配对码和 QR（同一个邀请生命周期）
输入配对码 → 查找本次匿名邀请 → 房主接受 → 双方身份校验码 → 认证/建网
扫描 QR → 验证邀请格式及有效性 → 房主接受 → 签名邀请绑定的身份握手/建网
附近设备 → 主动选择匿名候选 → 房主接受 → 双方身份校验码 → 认证/建网
全部检查成功 → 同一无游戏的连接大厅 → 保存好友 → 原游戏大厅选游戏
```

输入接受 6 位 ASCII 数字，包括前导零；去除粘贴内容首尾空白，不静默截断、多余字符不接受。输入不完整时不发请求；错误只在提交后或输入完成时显示，避免每键报错。提交期间不重复请求。错码、过期、不在附近、已失效各有固定原因和恢复动作，不显示未验证的身份。

原协议只有 BLE_ANONYMOUS 和 QR 两种 route，**并不存在现成的六位手输邀请查找能力**。本次新增入口需要实现计划中的 P2 协议补充，不能把示例 `482619`、SAS、二维码文本或裸 Wi-Fi 信息直接复用为口令。手输码只能定位临时匿名邀请；通过旧 BLE/SAS 身份握手提供认证，不引入第三套认证协议或互联网房间服务器。协议补充未通过时保留该入口和明确不可用原因，不伪造成功，也不得宣称全功能完成。

邀请有效期采用原设计 60 秒连续时钟，产品读真实剩余时间。作废、超时、重生成、取消后迟到结果均不可复活旧请求；QR 保留原规范单次消费语义。新旧邀请码/QR 必须绑定同一被更新的邀请 generation。

### 4.2 权限与错误

- 进入附近页面后才按阶段申请相关权限；点击扫码才申请相机。相机拒绝不禁用可工作的输入码/发现路径。
- 输入码仍可能需要附近发现权限，不宣传为绕过 BLE 权限的离线万能入口。
- Wi-Fi 系统确认与每 session 的一次预算按原设计；拒绝不循环弹窗。重试文案区分同 session 合法重试与结束后创建新邀请。
- 阶段顺序：权限 → 发现 → 认证 → Wi-Fi → QUIC → 版本 → codec。首个失败阶段显示原因，之前已通过，之后尚未开始；不要把未开始的步骤全标红。
- 认证失败/二维码篡改不能在原请求内自动重试或降级明文。单人功能继续可用。

## 5. 本局配置与文件

邀请者只是默认主机；network owner、QUIC listener、authority 与 P1/P2 不互相等同。N09 主机选择显示候选能力与资源风险；不可选择项有明确原因。主机和座位可由用户提出变更，但最终配置必须两端一致。

N09 首屏：游戏名称、文件状态、主机、座位、本机声音开关、双方待确认/已确认状态、相同的待确认配置短码，以及固定可见的确认动作。
“游戏与连接详情”包含好友身份短码、候选能力、风险、network owner、ROM 身份、两端是否已有、传输许可/进度、MultiplayerProfile 验证状态与自动模式结果。两端独立声音设置在各自本机生效，不改变对方声音。

单端确认绑定完整 pending-config fingerprint，UI 短码只供人工对照。绑定游戏身份、主机、seat、模式及能力计划；任一变化立即使双方确认失效并清晰提示。双方读到同一配置且分别确认后才允许开局。

模式只读：满足原门禁自动 DUAL，否则合法 HOST_STREAM；无强制模式开关、无额外逐局模式确认。文件缺失不意味着必须传输：STREAM 自身不传 ROM。独立补齐流程要求发送方同意、接收方同意、实际进度、通用文件校验、导入许可；拒绝或取消不隐含同意其他操作。

游戏内继续沿用旧设计 D6–D10：正常状态在既有暂停抽屉，冻结/断线用顶部不可忽略状态条；根据真实能力给出接管、继续单人、保存结束及禁用原因。不将本次大厅状态改成永久游戏 HUD，不静默改变 authority，不自动合并分支。

## 6. 三端视觉与尺寸合同

所有几何值使用安全区内的逻辑单位：Android dp、Harmony vp、iOS pt。同尺寸、语言与文字倍率下，应用结构、顺序、层级、颜色令牌和交互命中区域一致；字体采用平台系统中文/拉丁字体，字形抗锯齿差异不作为不同 UX。

| 元素 | 统一规则 |
|---|---|
| 页面 | 100% 可用宽度，子内容 min-width=0 等价约束；安全区只由最外层消费一次 |
| 现有大厅 | 保留 30% 详情 / 70% 游戏网格、原两行横向浏览、原搜索及工具入口 |
| 联机页 | 可用宽度 >580：左 224、间距 18、右剩余；≤580：纵向重排，按钮可换行，不缩字挤压 |
| 顶栏 | 基准 64；大厅现有紧凑/大字策略继续保留，右上角状态不覆盖分类或工具 |
| 正常按钮 | 至少 48×48 命中区域；主文字不得省略成图标 |
| 底部动作 | 固定在页面安全区底部的独立布局区；正文与底栏分别测量、正文可滚动 |
| 底部主按钮 | 宽度为内容所需，最小 160、最大可用宽度；**禁止继承大厅主按钮的整行 100% 宽度后与提示并排** |
| 并列弹窗动作 | 等分剩余宽度，min-width=0；文字换行，窄屏不足时堆叠 |
| 大厅主按钮 | 仍占左侧详情容器宽度；只在详情内为整行按钮 |
| 二维码 | 保持正方形、足够静区与对比；不拉伸。样稿中的伪 QR 只用于排版，正式产品必须编码真实协议邀请 |
| 文字/输入 | 大字倍率 1.0/1.3/2.0，不截断原因；软键盘开启时输入、错误和主动作可达 |
| 横向滚动 | 只允许原大厅游戏网格；页面主体、配对码页、底栏、弹窗不能产生横向滚动 |

联机页共同暗色令牌：background `#121316`、surface `#1B1D22`、raised `#292B31`、text `#F4EFE6`、muted `#BEB8AE`、primary `#FF6B5E`。颜色不能是状态的唯一表达。三端使用同一组线性图标语义与尺寸；不在 ArkUI 页面另写不同主题，不用平台默认 List 替代批准的联机双栏。

相同输入条件下应用内容框允许 ≤2 逻辑单位的栅格化偏差；任何可点击控件被遮挡、横向溢出、顺序改变、关键文案不同或状态错误均为不通过。不同设备的物理像素数不直接作等尺寸比较。

## 7. 单一状态与跨端接口

| 所有者 | 数据与职责 |
|---|---|
| shared session | 邀请 generation/期限、认证、权限能力原因映射、连接阶段、verified peer、候选主机、seat、pending config、双方确认、文件许可、重连与终止 |
| shared product policy | 入口状态投影、页面可用动作、三值游戏能力与稳定过滤、布局策略输入输出、状态/原因码 |
| 平台适配 | BLE/相机/Wi-Fi/安全存储、系统授权结果、实际媒体与网络能力；通过现有 JNI/NAPI/ObjC++ binding 回 shared |
| 本机 UI | 未提交输入、焦点、页面展开状态、分类/搜索/筛选偏好；不自行宣布配对成功或合成 peer 身份 |

继续使用 `shared/include/flynes/flynes_session.h`；平台不得建立三套协议 DTO。三端从同一语义 fixture 验证相同 screen、文字 key、可用动作和阶段。UI 测试可以注入模拟 adapter，但发布构建必须不能启用该注入。

## 8. 统一验收用例

| Case | 输入/动作 | 三端共同断言 |
|---|---|---|
| C01 | 无连接进入大厅 | 附近联机；四分类、搜索、原详情/网格均保留 |
| C02 | 任一分类 × 双人开关 × 搜索 × connect/disconnect | 连接事件不改分类/开关/查询；交集与顺序正确 |
| C03 | 内置仅单人，开启支持双人 | 零结果留在内置；关闭仅清除开关 |
| C04 | 创建、输入码、扫码 | 三动作首屏可见，未选游戏也可进入 |
| C05 | `012345`、空、5位、7位、字母、过期码 | 前导零保留；不合法不发请求；过期明确失败 |
