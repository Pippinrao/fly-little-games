# FlyNES 游戏大厅快速启动设计

## 背景与目标

Android 游戏大厅在 2,000 个以上游戏时启动明显变慢。现有启动路径在
`Application.onCreate()` 中同步创建 native 应用，打开完整 catalog；随后逐条跨
JNI 投影游戏，并为每个游戏单独查询用户状态；大厅等待这些工作和内置游戏重复
扫描完成后才显示。即使只有内置游戏，当前模拟器冷进程启动到 catalog 提交也约
为 1.45 秒。

本次优化的核心目标是：存在一份成功生成的 2,000+ 游戏大厅缓存时，在固定 Android
模拟器上以冷应用进程连续启动，启动请求发出到完整缓存列表首次可见的 P95 不超过
500 毫秒。测试不清除应用数据或系统页缓存；每次启动前强制停止应用，并使用应用内
时间戳标记“启动请求已接收”和“首个完整快照已提交到可见 RecyclerView”。至少运行
10 次，报告每次数据与 P95。

首次导入或缓存损坏不承诺在 500 毫秒内扫描完 2,000 个 ROM。此时大厅应在 500
毫秒内显示可交互的空状态或上次有效快照，扫描只在后台执行一次，成功后持久化供
后续启动复用。不得用截断列表、固定延时或跳过数据正确性校验来满足指标。

## 范围

本轮聚焦已复现退化的 Android 大厅启动路径，并允许为消除 JNI N+1 调用增加小型、
跨平台安全的 shared/native 批量读取接口。HarmonyOS 与 iOS 的大厅 UI 改造不在本轮
范围内，避免与独立的三端双向联机任务交叉修改；共享 catalog 的持久化语义和游戏
身份规则保持不变。

外部目录仅在首次导入、用户主动刷新、来源配置变更或系统明确报告访问权限变化时
扫描。普通应用启动不遍历 ROM 目录。内置 ROM 仅在内置清单指纹或 catalog schema
变化时重新扫描，不再每次启动都复制、哈希和提交七个资源文件。

## 架构

### 两阶段启动协调器

新增一个职责单一的 Android catalog 启动协调器，将大厅可见性与 native catalog
就绪状态分开：

1. **快速阶段**在专用 I/O 执行器读取原子大厅快照，校验 envelope 后发布不可变的
   `GameCatalog`/展示投影。此阶段不创建 `FlyNesApp`、不打开 native catalog、
   不访问 ROM 文件，也不逐条跨 JNI 查询。
2. **校验阶段**在后台惰性创建 native 应用，读取 generation 和来源元数据。若缓存
   generation、schema、内置清单指纹及来源版本均匹配，则直接结束，不枚举 catalog，
   不扫描内置或外部 ROM；若不匹配，则后台重建并原子发布新快照。

`FlyNesApplication.onCreate()` 只装配轻量依赖并启动快速阶段，不能同步等待 native
初始化。`HomeActivity` 订阅快照流：缓存命中时直接显示完整快照；缓存缺失时先显示
加载/空状态，后台首次建库成功后再替换。一个进程内的多个订阅者共享同一次初始化
和重建任务。

### 持久化快照

复用 `AndroidAtomicCatalogStateStore` 的原子文件策略，扩展为带 envelope 的大厅快照。
envelope 至少包含：

- 快照 schema 版本；
- native catalog generation；
- 内置游戏清单内容指纹；
- 来源 epoch：每次导入、删除、用户主动刷新或检测到持久 URI 权限集合变化时递增；
- 完整展示投影，包括 canonical ID、标题、来源、收藏/最近状态、排序和搜索所需字段；
- payload 长度与校验和，用于识别截断或损坏文件。

写入必须先生成临时文件、同步并校验，再原子替换当前快照。只有完整 rebuild 成功后
才更新 envelope；取消、异常、权限丢失或进程退出不能覆盖最后一份有效快照。schema
不兼容、校验和错误或字段越界时忽略该文件并进入后台重建，不让解析异常阻塞 UI。

缓存是可重建的展示索引，不是 ROM 真值来源。它可以在后台校验期间以
last-known-good 方式展示，但不能单独授权游戏启动。

### 后台重建与 JNI

后台重建保留现有 catalog 的 canonical ID、去重和原子提交规则，但消除当前双重
`refreshNativeView()` 以及“每条 catalog entry 再调用一次 `userState(id)`”的 N+1
模式。shared/native 提供一次批量快照读取，其中每条记录已经带有重建展示投影所需
的用户状态；Android 只做一次边界调用并在后台构造、排序不可变列表。

内置游戏清单指纹直接由版本化的 `builtin-games.json` 内容及相关 schema 计算。指纹
未变化时不复制或哈希内置 ROM。外部来源变化由导入、删除、刷新和权限回调显式增加
来源版本；普通启动不通过目录全扫描来猜测是否变化。

若 native generation 与快照一致，但来源权限已被系统明确撤销，协调器标记对应来源
失效并执行一次后台重建。无法访问的来源不会触发紧密重试；仅在下一次来源事件、用户
主动刷新或下次进程启动时重试。

## UI 与懒加载

大厅首次收到快照时直接提交已预计算排序的不可变列表，不在主线程重新遍历、聚合和
排序 2,000+ 条记录。后续后台快照通过稳定 canonical ID 和差量更新提交，避免
`notifyDataSetChanged()` 造成全量重绑。RecyclerView 继续只创建可见卡片。

封面加载保持按可见项触发，并增加 canonical ID 级别的进程内请求合并：同一封面正在
读取或解码时，重绑只加入等待者，不重复提交磁盘任务。holder 复用后仍校验绑定 token，
只把结果设置给当前游戏；离屏等待者可取消，但共享解码只有在没有等待者时才取消。
本次缓存只在本次进程复用解码结果，不引入新的持久封面格式。

## 启动游戏时的一致性

用户可以在后台 native 初始化完成前浏览和选择缓存中的游戏。点击启动后，启动协调器
等待同一个 native 就绪 future，然后以 canonical ID 重新解析真实条目，验证来源权限、
ROM 可读性和现有哈希/身份约束。验证成功才进入模拟器；缓存条目已删除、来源不可访问
或身份不匹配时，留在大厅显示可恢复错误，并触发一次后台快照修正。

同一进程中多个启动请求必须串行化；新的明确选择可以替换尚未开始的旧请求，已经进入
模拟器的请求不被后台刷新打断。任何情况下都不得直接把缓存路径传给核心绕过 native
catalog 校验。

## 失败处理

- **无缓存：** 500 毫秒内显示加载/空状态，后台建立 catalog 和首份快照。
- **缓存损坏或版本不兼容：** 隔离坏文件，保留应用可用性，后台重建；不反复解析同一
  坏文件。
- **后台初始化失败：** 若有有效快照则继续只读浏览并显示非阻塞状态；启动游戏时给出
  明确错误。若无快照则展示可重试错误。
- **重建失败或被取消：** 保留最后有效快照和 generation，不写半成品。
- **权限撤销或来源删除：** 后台差量发布移除项；若用户正准备启动该项，真实校验优先
  并阻止启动。
- **低存储空间：** 原子写失败不删除旧快照；记录可诊断错误并在下次合法触发点重试。

## 测试与验收

所有产品行为按 TDD 实施：先增加能在旧实现上失败的断言并记录 RED，再写最小实现，
最后运行相关回归。覆盖以下层次：

1. **JVM 单元测试：** 有效/缺失/损坏/旧 schema 快照；generation 和清单指纹匹配与
   失配；缓存命中不创建同步 native backend；普通启动不扫描外部来源或内置 ROM；
   后台失败保留旧快照；启动请求等待 native 并重新校验；重复封面请求只解码一次。
2. **shared/native 主机测试：** 批量快照与逐条语义一致，包含用户状态，generation
   稳定，空库和 2,000+ 条目无遗漏、重复或顺序不确定性。
3. **Android instrumentation：** 使用仓库允许的合成 metadata/fixture 构造至少
   2,000 个 catalog 条目；验证缓存列表完整可见、滚动按需绑定、后台替换保持选择，
   缓存条目在 native 未就绪时点击会等待并完成真实校验。测试不得提交私有 ROM。
4. **性能门禁：** 固定模拟器、release-like 构建、已有有效 2,000+ 条目缓存、每轮先
   `force-stop`，至少 10 次冷进程启动。采集启动接收、快照读取、列表提交、首帧可见和
   后台 native 就绪时间；“完整缓存列表可见”指 adapter 已持有全部 2,000+ 条目且首个
   游戏卡片完成 pre-draw。“启动接收到完整缓存列表可见”的 P95 必须不超过 500 毫秒，
   同时确认启动阶段的 ROM 文件扫描次数为 0、逐条 `userState` JNI 调用次数为 0。
5. **首次建库场景：** 清除测试缓存后验证 UI 在 500 毫秒内进入可交互加载/空状态，
   扫描在后台只运行一次，生成缓存；第二次冷启动必须通过缓存性能门禁。

Android shared/native 改动完成后运行主机 CTest 与 Android 单元测试；大厅或列表行为
改动完成后运行模拟器 instrumentation。最终报告测试命令、2,000+ 数据规模、每轮耗时、
P95、缓存命中/重建日志计数以及尚未由模拟器证明的硬件属性。模拟器结果只证明功能和
启动时间，不外推实体机功耗、温度或存储性能。

## 非目标

本轮不改变 ROM 内容规则、catalog 身份、存档格式、联机协议或三端联机功能；不新增
持久好友、网络恢复或硬件模式；不以分页截断游戏库，也不把用户主动刷新移除。若完整
缓存反序列化本身仍无法满足 500 毫秒，后续可以在保持本设计接口不变的前提下切换为
分段/内存映射格式，但本轮先用测量结果决定，不预先增加该复杂度。
