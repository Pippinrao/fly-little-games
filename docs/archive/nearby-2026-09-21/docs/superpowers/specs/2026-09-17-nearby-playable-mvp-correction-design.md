# Nearby 可玩首版纠偏方案

日期：2026-09-17。依据：用户要求恢复获批 UX、先交付能玩的版本、复杂功能后置。本文件是执行范围与技术方案，未实施；具体首平台/入口取舍是本方案建议，不能冒充已经获批的 UX 改版。

相关：[现状审计](../../audits/2026-09-17-nearby-ux-course-correction-audit.md)、[执行计划](../plans/2026-09-17-nearby-playable-mvp-correction-plan.md)、[原始交互稿](assets/nearby-ui-parity-review.html)、[获批设计](2026-09-13-nearby-ui-parity-design.md)。

执行细则：[逐页 UX 恢复卡](../plans/2026-09-17-nearby-ux-restoration-task-cards.md)、[可玩链路执行卡](../plans/2026-09-17-nearby-playable-engine-task-cards.md)。本版已区分 M0 首局技术可玩、M1 首平台原稿基本版、M2 三端候选；M0 的临时能力限制不能固化为最终 UX。

## 1. 首版交付定义

两名玩家从应用内创建/加入，验证身份，返回原游戏大厅，选择两端均已合法拥有、同一内容身份且 profile 已验证的游戏，各自确认同一配置后进入游戏；P1/P2 输入分别生效，两端本地运行 NES core 并显示画面/播放声音；能够暂停、继续、结束回大厅；断线冻结并允许明确结束。

首版只支持两人 DUAL。不含 ROM 网络传输、不含画面串流、不含主机迁移或故障自动恢复。不是承诺任意 ROM 都支持双人；UNKNOWN 保持 UNKNOWN。

推荐先完成 Android↔Android 纵向闭环，再推广 Harmony/iOS。原因是当前本机可用 Android 构建与模拟器工具，三套未通链同时开发会放大反馈周期。这是交付顺序，不取消三端目标，也不把 Android 完成算作三端完成。

真机验收仍 NOT_RUN。无物理设备测试时只能交付“模拟器/非真机环境可玩候选版”，不能宣称附近无线及跨平台真机已验收。若模拟器无法运行真实发现路径，记该能力 BLOCKED；测试发现替身的成功只认证后续链路。

## 2. 保持原稿的用户主线

```text
原游戏大厅 G00 → 附近联机 N00
房主：创建 N01                       加入者：输入配对码 N02
房主：匿名请求 N05 ← 请求加入 → 加入者：等待 N04
双方身份校验 N06 → 验证/连接 N07 → 已连接 N08
→ 返回原游戏大厅 G00 → 本局配置 N09 → 双方确认 → 游戏
→ 暂停抽屉 / 结束本局回原大厅（连接仍在）
```

建议首条可用加入路径为输入配对码，复用已实现的匿名发现/握手；附近候选可复用同一路径。QR 保留 N00 原位置与 N03 页面结构，若首版未接相机/签名邀请，清楚显示不可用原因及“改用输入配对码”，不得点击扫码后伪装成扫码成功。QR 完整实现作为下一小版本，不阻塞第一局。

必须保持：

- G00 原 30% 详情 / 70% 两行横向网格、四分类、搜索工具；“支持双人”是数量行独立开关。
- N00 左侧文案与创建/输入码/扫码三动作，右侧设备/好友；技术阶段不占据首页。
- N01 真邀请期限、generation、取消/重生成；N04/N05 未认证匿名；N06 邀请码与身份校验码区分。
- N08 身份、通道及兼容性验证全部完成才显示获批文案“双人联机中”。
- N09 首屏只有本局必要信息：游戏/文件、主机、P1/P2、模式、声音、配置短码、双方确认；网络 owner、ROM hash 等放“游戏与连接详情”。
- 宽度 >580 左 224/间距 18，≤580 重排；48 命中区、固定独立底栏、非游戏网格无水平溢出；色令牌按原设计。

获批稿中的示例好友、游戏、配对码、模拟按钮、伪 QR 永不进入正式数据。

## 3. 首版范围及后置行为

| 能力 | 首版要求 | 后置部分/暂不可用时行为 |
|---|---|---|
| 认证连接 | 真实房主接受 + 双端 SAS + 加密 channel/link 校验 | 不降低身份验证；禁止明文或 UI 自报成功 |
| 邀请方式 | 输入码实际可用；附近候选复用已有实现 | QR 完整链可后置，入口保留解释与切换 |
| 文件与 profile | 两端同 ROM、同核心兼容配置，至少一份可合法用于回归的已验证双人样本 | 缺文件显示“请双方先导入同一游戏”；不自动传输 |
| 主机/座位 | M0 可先验证默认角色；M1 按原稿支持开局前合法主机选择/P1-P2 对换，变更撤销双确认 | 游戏中主机迁移后置；不得把开局前选择误删成固定角色 |
| 开局 | 配置一致 + 两端独立确认 + 两端 runtime ready 才运行 | 不把 SELECT/START_LOCAL 代替双方确认 |
| 声音 | 各端本地开关，不改对方设置 | 不做网络音视频编码 |
| 暂停/继续 | 健康连接内双方按同一帧边界暂停/恢复；不重置或丢失另一端输入 | 故障重连恢复后置；不可把“暂停后无法继续”称完整可玩 |
| 结束/换游戏 | 明确结束旧局，拒绝旧局输入；回大厅保留连接，下一局重新确认 | 中途接管、保存后跨设备恢复、分支合并后置 |
| 断线 | 超时/非法包冻结、可结束/断开，单人功能可重新进入 | 不静默转单人、不自动迁移、不承诺恢复 |
| 好友 | M0 先打通身份连接；M1 包含认证后的基本持久保存，保存成功才显示“好友已保存” | 自动邀请、改名/拉黑/身份重置完整 UX 后置，入口明确状态 |

QR 与完整好友能力延期应记录在版本能力表，对应完整原稿功能仍是未完成。扫码页结构、开局前角色选择、好友基本保存不是随意改稿的空间；准确顺序和验收分别见 UX-07、ENG-07、ENG-04。不得修改原稿来掩盖差异。

## 4. 最小实现接线

复用 NestopiaUE、现有 `flynes_runtime`、Quinn/rustls、已有 V2 engine 和平台安全/网络 API，不重新实现模拟器、TLS 或 QUIC。现有 fake runtime/transport 保留作快速测试，产品实现通过同一端口替换它们。

```text
原生页面（动作/只读快照）
  → 平台 session owner / JNI、NAPI、ObjC++
    → 一个 V2 SessionEngine（连接域 + 游戏域）
      → 原生发现/权限/安全存储/网络端口 → Quinn
      → 配置与双确认 → DUAL scheduler → 真实 NES runtime
                                          → 现有本地渲染/音频
```

### 4.1 配置与开局

新增或完善引擎拥有的 pending config，而不是在 UI 造配置对象。配置至少绑定内容身份、core/profile 版本、运行选项、会话/游戏 epoch、authority、seat、DUAL 能力结果及 revision。复用已有 wire/schema 合同；确有缺口时由唯一集成人补充一个最小版本，先明确字节格式与负例，不新建平行协议。

每端“确认入局”绑定完整 fingerprint；短码只显示。任何配置变更撤销双方确认；旧 approval token 和旧 generation 被拒绝。双方确认与 runtime ready 都完成后才发出同一开局帧边界，才允许快照 GAME_RUNNING。

当前 START_DUAL 可以成为引擎内部实施步骤，不能继续作为用户绕过 N09 的入口。`dual_seats_confirmed` 必须来自真实协商确认，不能由 `selected_` 推导。

### 4.2 真实运行时与内容

目录以共享 catalog 的 typed choice ref 找内容；UI 不传裸 hash、不猜 profile。runtime adapter 装载同一 ROM/设置，通过既有 core/runtime API 执行帧与导出/导入状态，使用现有视频/PCM 输出。一次游戏只有 scheduler 拥有步进时钟，原本单人播放线程不得同时 step 同一实例。

至少先用合法双人测试样本跑跨输入轨迹；不能硬编码内置游戏名/ID。样本可来自授权 homebrew 或受控测试夹具；私有 ROM 不提交、不打印、不迁移到 content。

### 4.3 平台 owner 与真实网络

平台创建一个真实 V2 engine，并提供 clock、executor、platform state、discovery、crypto/secure store、ObjectStore、bearer、QUIC、content、runtime 所需端口。页面切换不销毁朋友连接；旧邀请码 bridge 逐步委托此 owner，不同时维护两套连接真相。

QUIC crate 自测只是供应组件证据。需要由两个真实 engine 驱动产品 Quinn provider 的集成测试，不能让 LoopbackTransport 在同一测试中代收发而标成真网。

### 4.4 稳定性底线与扩展

健康会话的暂停/继续、显式结束和下一局输入隔离属于基本玩法；它们不应为了复用全面恢复设计而依赖所有 WAL/迁移事务完成。若既有协议不能安全表达，先补最小 control 合同并做负例，保留自动故障恢复禁用。

保留 content port、recovery 组件和 STREAM 能力位的扩展边界，未交付功能不发布可执行 action。隔离已有后置代码，不删除他人未提交实现，也不强行全部合入首版。

## 5. 验收层级

| 层级 | 实测对象 | 可以宣称 |
|---|---|---|
| L1 | codec/scheduler + fake runtime/transport | 组件或 engine 夹具通过 |
| L2 | 两个 V2 engine + 真 Quinn + 真 NES runtime + 合法 ROM | 非原生真实游戏运行链通过 |
| L3 | 两个原生应用实例，从原界面完成入局、画面/声音/双输入/暂停/结束 | 标注具体模拟器/网络条件的可玩候选版 |
| L4 | 各真实设备组合、无线发现、系统授权/后台与性能 | 真机联机验收；本轮 NOT_RUN |

首版必须达到 L2，并在首平台达到 L3 才能叫“能玩的候选版”。若平台环境不支持真实无线发现，可记录替身边界，但不能因此将 L4 提前通过。三个平台各自 L3 通过后，才叫“三端非真机候选版”。

验收不使用笼统“后端完成率”。每个报告列明真实/替身端口、源树、配置、运行时、样本标识、测试结果和尚未支持能力。
