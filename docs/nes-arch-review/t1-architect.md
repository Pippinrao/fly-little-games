# t1 · 系统架构与可移植性评估（architect）

> 领域：模块边界、目录结构、C ABI 接口设计、JNI 桥接策略、可移植性（鸿蒙/iOS 的 NDK 差异、OHOS 对 C++/ArkTS 的支持、iOS 对 C++ 的桥接）、构建系统（Gradle+CMake+NDK 多 ABI）。
> 关键外部事实（已核实）：① HarmonyOS **NEXT（HarmonyOS 5，2024）** 已移除 AOSP，**没有 Java/JNI**，外壳是 **ArkTS**、原生桥接是 **NAPI（Node-API，C 风格）**；旧 HarmonyOS 1–4 才是 Java+JNI，但那套兼容层已被弃用方向取代。② NestopiaUE 为 GPLv2、C++14、`source/core` 平台无关。③ iOS 无 JNI/NDK，用 Objective-C++（`.mm`）+ `extern "C"` 桥接，且**只能在 macOS/Xcode 上构建签名**。

---

## 0. 一句话结论（TL;DR）

这套「C++ 核心 + Java 外壳 + JNI」的骨架方向正确，但「将来移植鸿蒙/iOS **核心不动、只换壳**」是一个**过度乐观的表述**：鸿蒙 NEXT 没有 Java/JNI（外壳是 ArkTS、桥是 NAPI），iOS 没有 JNI（桥是 ObjC++）。真正能跨三平台复用的只有 **「平台无关 core + 一个桥接无关的 C ABI」**，壳与桥都必须重写。因此整个架构的成败**不在 Android 外壳，而在 C ABI 边界的纪律**：只要 core/ABI 泄漏任何 Android/JNI 类型，阶段 3 就从「换壳」退化为「重写」。这是最该先拷问用户的问题。

---

## ① 按优先级排序的尖锐问题 / 决策点清单

> 优先级：P0 = 决定架构走向，必须先答；P1 = 影响阶段 0~1 的实现与后续返工；P2 = 影响阶段 2~3 或属于执行细节。

### Q1 [P0] 「只换壳」的前提：core 与 C ABI 是否做到**零平台依赖**？

- **为什么重要**：这是整套可移植性赌注的地基。如果 C ABI 里出现 `JNIEnv`、`jobject`、`ANativeWindow`、`AAudioStream`、Java 对象引用，或者 core 直接 `#include` 平台头文件，那么鸿蒙/iOS 移植就不是「换壳」而是「顺着平台调用重写」。地基错了，阶段 3 的承诺就是空的。
- **建议选项与取舍**：
  - **A. 严格 C ABI**：core 只暴露 `extern "C"` + 不透明句柄（`void* nes_ctx`）+ 原始字节缓冲 + 回调；视频/音频/输入/文件/时钟/日志全部由外壳经 ABI 注入，core 内部**不含任何平台头文件**。
    - 取舍：前期抽象与样板更多，但移植真实省力、可用无头测试覆盖、各平台适配层极薄。
  - **B. 宽松边界**：core 直接调用平台 API（`ANativeWindow` 等），靠 `#ifdef __ANDROID__` 分平台。
    - 取舍：前期快，但每个新平台都要在 core 里加分支，移植 = 重写，且 core 无法无头单元测试。
- **推荐**：**A**。并把「零平台依赖」写成**可执行约束**而非口号：CI 里加一个「裸 core」编译目标（在不含任何 NDK/平台头的最小 clang 环境下编译 `core/`），用 `#include` 白名单或脚本检查禁止 core 引用平台头。这条约束一旦立住，Q1 之后的每个问题都顺理成章。

### Q2 [P0] 分层与「自研逻辑」归属：金手指/补丁/存档/内存编辑这些**你的代码**放哪一层？

- **为什么重要**：任务反复强调「C++ 主线、核心不动」，但「魔改（作弊码增强、存档/内存编辑、调试器）」这些是**你自己要写的逻辑**，不是 Nestopia 自带功能。它们放哪，直接决定：①是否违背「核心不动」；②移植时要不要重写；③NestopiaUE 升级时是否痛苦；④ GPL 传染面是否缠绕（与 t5 协同）。
- **建议选项与取舍**：
  - **A. 自研逻辑进 core 层（C++，平台无关）**，NestopiaUE 只当库引用、**不改其源文件**（vendor + 最小 diff），自研模块独立目录（`core/src/{save,cheat,patch,mem,state}`）。
    - 取舍：前期多写 C++、要更多 C ABI 面，但移植免费、可无头测试、Nestopia 可跟随 upstream 升级。
  - **B. 自研逻辑放壳层（Java/Kotlin）**：用平台生态省事。
    - 取舍：上手快，但「魔改」逻辑每次移植都要重写，且强耦合 Java，违背「核心不动」的初衷。
- **推荐**：**A**。明确一条纪律：**「你的业务逻辑」与「Nestopia 的仿真逻辑」物理隔离**——NestopiaUE 以 vendor 子目录进入、只打最小必要补丁（补丁单独归档、可重新 rebase），自研模块通过 C ABI 暴露。这同时给 t5 的 GPL 边界留出干净接缝。

### Q3 [P0] 跨边界**数据契约**：视频/音频/输入/文件走 push 还是 pull？缓冲**谁拥有**？

- **为什么重要**：这是「核心不动」能落地的第二块地基，也直接决定 JNI 开销（每帧几次拷贝）、省电（t3）、以及 iOS/鸿蒙是否真能「只换壳」。契约定错，后期优化（低延迟音频、省电）会撞墙。
- **建议选项与取舍**：
  - **A. Pull 模型**：外壳（音频/渲染线程）主动调 `nes_audio_pull(ctx, buf, frames)` / `nes_video_pull(ctx, buf)`；缓冲由调用方提供。
    - 取舍：简单、无跨线程回调、缓冲生命周期清晰（避免 JNI 拷贝），但节奏控制责任在外壳。
  - **B. Push 模型**：core 主动回调 `on_frame`/`on_audio`（需跨线程回调 + 线程安全）。
    - 取舍：适合低延迟但线程复杂度高，且 iOS/鸿蒙适配层都要处理线程回调。
  - **C. 混合**：音频 pull（音频线程定节奏、环形缓冲）、视频 pull 或「外壳给外部缓冲、core 写入」。
- **推荐**：**C**。**音频以 pull 为节拍源**（音频线程决定采样节奏、驱动模拟步进），**视频由渲染线程 pull**；所有跨边界缓冲由**外壳（或共享内存）持有**，core 不负责分配/释放跨边界内存。**ROM 一律以「字节指针 + 长度」输入，core 永不碰文件系统**（SAF/私有目录/assets 的差异全部留在壳层）。这条「core 不碰文件系统/不碰平台内存」的约定，是三平台可移植的核心前提。

### Q4 [P1] 线程与主循环归属：**谁拥有模拟循环**？生命周期契约是什么？

- **为什么重要**：决定省电（后台/息屏暂停、降帧）、暂停/恢复、iOS/鸿蒙移植难度，也是 core 与壳最大的隐性耦合点。现在不定清，后面「飞机上省电」「切后台要存档」都会返工。
- **建议选项与取舍**：
  - **A. core 拥有线程**：`nes_run(ctx)` 阻塞推进、内部定时（sleep/忙等）。
    - 取舍：实现简单，但壳难以控制暂停/节流，省电与后台处理棘手。
  - **B. 壳拥有循环**：core 只提供 `nes_step_frame()` / `nes_run_frame()` 单步接口，由壳的 vsync/音频回调驱动。
    - 取舍：壳完全可控（降帧、暂停、省电），iOS/鸿蒙也自然；代价是时序精度责任交给壳。
  - **C. core 提供 `run()`，但以音频回调为节拍源**（音频节奏驱动推进）。
- **推荐**：**B/C 混合**：core 提供**单帧步进**接口（而不是只能 `run()`），由**音频线程节奏驱动推进、渲染线程取帧**，同步策略归壳持有；core 内**禁止 sleep/忙等**。同时把**生命周期契约**写进 ABI：`pause()` / `resume()` / `save_state()` 幂等且可被后台回调安全调用。

### Q5 [P1] C ABI 的**版本化与冻结**策略：谁来保证 NestopiaUE 升级不破坏 ABI？

- **为什么重要**：NestopiaUE 会升级；若 ABI 直接映射 Nestopia 内部类型/布局，升级 = 破坏所有壳。基座阶段不把版本机制定下来，就是埋雷。
- **建议选项与取舍**：
  - **A. 经典稳定 C ABI**：`nes_api_version()` + 所有跨边界 struct 带 `size`/`version` 字段（Vulkan/OpenGL 风格），不透明句柄隐藏全部内部布局。
    - 取舍：样板略多，但升级可向前兼容、可 ABI 测试。
  - **B. 语义化版本 + 编译期断言**：靠头文件宏 + static_assert 约束。
  - **C. 不版本化，锁定 NestopiaUE 提交点**：最简单，但升级困难、无法跟进上游 bug 修复。
- **推荐**：**A（至少做到 A 的最小集）**：`nes_api_version()` + 每个跨边界 struct 带 `size`/`version` + 不透明句柄。写一条「ABI 稳定性测试」门禁（比对导出符号表 diff / golden 结构体布局），防止任何人无意破坏。

### Q6 [P1] JNI 桥接策略：**单一 .so 静态链** 还是 **拆出纯 C ABI 的 .so**？符号可见性如何管理？

- **为什么重要**：影响包体、构建复杂度、升级粒度，以及 **GPL 边界（t5 领域，但架构上要先留缝）**。JNI 适配代码若与 Nestopia core 揉成一个 .so 且符号全导出，将来想拆动态边界/进程隔离就得重构。
- **建议选项与取舍**：
  - **A. 单一 `libnes.so`**：Nestopia core + C ABI + JNI 全静态链进一个 .so。
    - 取舍：最简单、无跨 .so 符号问题；但 JNI 适配与 core 耦合，GPL 传染面最大。
  - **B. 两层 .so**：`libcore.so`（纯 C ABI，无 JNI）+ `libbridge.so`（JNI 适配）。
    - 取舍：边界清晰、可独立测试、为 GPL 边界留余地；多一层 ELF 依赖与符号导出管理。
- **推荐**：**阶段 0 用 A 快速打通**，但**必须把 C ABI 写成独立编译单元 + 独立头文件边界**（`include/nes/`），JNI 适配只依赖该头文件。这样将来无需重构即可切到 B。符号一律 `-fvisibility=hidden` + 显式导出（版本脚本/`__attribute__((visibility("default")))`），避免 `.so` 泄漏 Nestopia 内部符号。

### Q7 [P1] 多 ABI 与 minSdk 取舍：放弃 32 位 x86 吗？armeabi-v7a 要吗？

- **为什么重要**：直接影响包体、构建矩阵、兼容面与上架（Google Play 已强制 64 位）。
- **建议选项与取舍**：
  - **A. 发布 `arm64-v8a` + `armeabi-v7a`，开发另加 `x86_64`（模拟器）**：覆盖面最广，但包体/构建时间增加。
  - **B. 发布只 `arm64-v8a`（+开发 `x86_64`）**：包体最小、构建最快，放弃极老设备。
- **推荐**：**发布 `arm64-v8a` 为主，`armeabi-v7a` 视目标机型决定（飞机上玩的多为现代机，可先不做 32 位）**；`x86_64`/`x86` 仅放在 `debug` buildType 用于本机模拟器加速。minSdk 建议 **≥ 21~24**（音频/渲染 API 与 NDK 支持更省事），targetSdk 用最新。NDK 版本**二选一并锁定**（27 或 28），写进 CI 与文档，避免「我本地能编、你本地不行」。

### Q8 [P2] 鸿蒙移植的目标：**HarmonyOS NEXT（ArkTS+NAPI）** 还是旧版 AOSP（Java+JNI）？

- **为什么重要**：这是「只换壳」最大的坑。**HarmonyOS NEXT 没有 Java**——外壳是 ArkTS、桥接是 NAPI（Node-API，C 风格），Java 壳根本带不过去；旧 HarmonyOS 1–4 才吃 Java+JNI，但那套 AOSP 兼容层已被弃用方向取代。
- **建议选项与取舍**：
  - **A. 认准 NEXT/OpenHarmony**：只保 core + C ABI 平台无关，将来写 **ArkTS 壳 + NAPI 适配**。
    - 取舍：与 Q1 一致，前期投入全在 ABI 抽象上，方向正确。
  - **B. 赌旧 HarmonyOS 复用 Java 壳**：短期省力，但方向已被 NEXT 弃用。
- **推荐**：**A**。请用户**明确回答「鸿蒙 = HarmonyOS NEXT / OpenHarmony」**。架构上把**桥接层做成可插拔适配器**（JNI / NAPI / ObjC++ 三个薄适配，共享同一 C ABI），壳层**不共享代码、只共享 C ABI**。把这条写进阶段 0 的目录与接口设计，别让「换壳」变成「换壳 + 换桥 + 换语言」的意外。

### Q9 [P2] iOS 移植的前置现实：**macOS/Xcode 工具链**与「Windows 开发」的矛盾如何提前处理？

- **为什么重要**：计划写的是「Windows + JDK + NDK」，但 **iOS 只能在 macOS 上构建与签名**，且 GPL 核心进 iOS App Store 有合规问题（t5）。这条前置现实不提前排，阶段 3 的 iOS 就会是「工具链 + 合规」双重空降。
- **建议选项与取舍**：
  - **A. 现在不投 iOS 工具链，只做「macOS 编译门禁」**：CI 加一个 macOS runner，保证 `core + C ABI` 在 macOS clang 下常绿编译。
    - 取舍：成本极低、防回归，把 iOS 可编译性前移，但不承诺阶段 0 出 iOS 壳。
  - **B. 阶段 3 再买 Mac / 开 CI**：临时抱佛脚。
- **推荐**：**A**。用 GitHub Actions 的 macOS runner 建一个「core 在 macOS 下编译」的常绿门禁（顺带验证无平台头依赖，与 Q1 同源）。iOS 壳与合规问题在阶段 3 前只做预研、不承诺交付。

### Q10 [P1] 基座阶段就要有的**横切件**：错误码 / 日志 / 配置 / 生命周期 / 测试与 CI。

- **为什么重要**：「可扩展基座」若缺错误码、日志、配置抽象、后台暂停、无头测试这几样横切件，后面每加一个功能（魔改、省电、上架）都要回头碰核心。模拟器最怕「跑起来了但没法定位为什么爆音/崩溃/丢帧」。
- **建议选项与取舍**：
  - **A. 阶段 0 就定**：错误码枚举 + 日志回调 + 配置键值（由壳持久化、core 无状态）+ 无头 golden 测试 + CI 构建矩阵。
    - 取舍：前期多投入，但避免大量返工。
  - **B. 后面补**：快，但技术债重。
- **推荐**：**A**。其中**无头 golden 测试**（对已知 ROM 跑 N 帧，比对帧 CRC / 截图哈希 / APU 采样哈希）是模拟器项目性价比最高的质量门禁，应作为基座的「完成定义」之一，而不是可选项。

### Q11 [P2] 基座抽象的上限：**过度工程**的反向风险如何控制？

- **为什么重要**：反向风险同样致命——「可扩展基座」如果被做成通用框架（插件化多内核、通用 frontend、跨一切平台），NES 项目会陷在抽象里，MVP 遥遥无期，违背「不着急上手玩、但要尽快有可玩闭环」。
- **建议选项与取舍**：
  - **A. 抽象只到「三平台换壳 + NestopiaUE 升级」所需程度**：四层（core / C ABI / 桥 / 壳），C ABI 只暴露本任务清单里列的能力，YAGNI 掉「多模拟器内核插件化」「通用录像/回放框架」等。
  - **B. 一步到位做通用模拟器框架**：过度设计。
- **推荐**：**A**。判断标准一句话：**「每加一层抽象，都要能被『三平台复用』或『NestopiaUE 升级』这两个理由之一买单」，否则砍掉**。

## ② 该领域主要风险与修正建议

| # | 风险 | 说明 | 修正建议 |
|---|------|------|----------|
| R1 | **「只换壳」幻觉** | core/ABI 一旦泄漏 `JNIEnv`/`ANativeWindow`/Java 对象，鸿蒙 NEXT（无 Java）与 iOS（无 JNI）移植退化为重写。 | 把「core 零平台依赖」固化为可执行约束：独立编译目标 + 平台头 include 白名单检查 + CI 门禁（见 Q1）。 |
| R2 | **C ABI 不稳定 → NestopiaUE 升级噩梦** | ABI 直接映射 Nestopia 内部类型/布局，升级即破坏。 | 不透明句柄 + `api_version()` + struct `size/version` 字段 + ABI 符号表 diff 测试（见 Q5）。 |
| R3 | **线程/时序模型设计错误** | 循环归属、回调线程安全、后台暂停没定清 → 后期省电/爆音/崩溃返工。 | 阶段 0 定死线程契约：音频节奏驱动、单帧步进、core 不忙等、生命周期幂等（见 Q4）。 |
| R4 | **多 ABI/符号/包体碎片化** | 无 `abiFilters`、符号全导出、不 strip → 包体虚胖、符号泄漏、构建不一致。 | 明确 abiFilters、`-fvisibility=hidden` + 显式导出、strip + `-Os` + LTO、锁定 NDK 版本（见 Q6/Q7）。 |
| R5 | **Windows 开发与 iOS/macOS 工具链割裂** | 「Windows 能跑」≠「iOS 能编」；阶段 3 才想起 macOS 已晚。 | macOS CI 编译门禁前移（见 Q9），把 iOS 可编译性作为持续约束而非交付项。 |
| R6 | **JNI 高频开销（每帧多次跨边界拷贝）** | 逐像素/逐采样跨 JNI → CPU 与功耗浪费，违背省电目标。 | bulk transfer + direct `ByteBuffer`/共享内存，最小化跨边界调用次数，缓冲由外壳持有（见 Q3）。 |
| R7 | **GPL 静态链的架构耦合** | JNI 适配与 GPL core 揉成一团，将来想拆动态边界/进程隔离要重构。 | C ABI 接缝独立成层（`include/nes/`），JNI 只依赖该头文件，预留拆 `.so` 的能力（见 Q6，合规细节归 t5）。 |
| R8 | **自研逻辑侵入 upstream 源** | 把魔改逻辑写进 Nestopia 源文件 → 升级/合并痛苦、GPL 面缠绕。 | vendor + 最小补丁 + 补丁归档，自研模块独立目录（见 Q2）。 |
| R9 | **过度工程（反向风险）** | 基座做成通用框架，MVP 遥遥无期。 | 抽象只到「三平台换壳 + Nestopia 升级」买单的程度，YAGNI 掉多内核插件化等（见 Q11）。 |

## ③ 路线中遗漏的东西（从系统架构角度）

1. **测试与 CI 完全缺失**（最高优先补）：无头 golden 测试、C ABI 稳定性测试、多 ABI 构建矩阵、macOS 编译门禁。基座阶段的「完成定义」应包含这些，而不是「能跑一帧就算过」。
2. **桥接层被低估为「只换壳」**：鸿蒙 NEXT = ArkTS + NAPI、iOS = ObjC++，均非 JNI。路线应把「桥接适配层（JNI/NAPI/ObjC++）」显式列为阶段 3 的独立工作量，并把 C ABI 设计成桥接无关。
3. **C ABI 版本化/冻结策略**未提及（Q5）。
4. **线程与同步契约**未定义：谁拥有循环、音频/视频节奏、回调线程安全、后台/息屏生命周期（Q4）。
5. **错误码 / 日志 / 配置 / 生命周期**抽象未列入阶段 0（Q10）。
6. **文件访问抽象边界**：core「不碰文件系统」的约定未定（SAF vs 私有目录 vs assets 的差异应全部留在壳层），这是「三平台换壳」的前提之一。
7. **输入抽象**：触屏按键映射、多手柄、外部手柄/键盘的 ABI 接口与默认键位未在基座定义（阶段 1 才提外部手柄，但 ABI 接口应在阶段 0 预留，避免阶段 1 改 ABI）。
8. **存档/即时存档的数据格式版本化与校验**：跨版本兼容、防损坏（SRAM 校验和、状态版本号）未提——这是「飞机上存档」的核心体验，损坏即灾难。
9. **为阶段 2 调试器预留的 ABI 钩子**：CPU/总线/内存访问接口若不在基座预留，调试器（阶段 2）会回头改 ABI。
10. **NDK/vendor 依赖锁定与可复现构建**：NDK 版本、NestopiaUE 提交点、第三方依赖的锁定与文档化未提（避免「我本地能编」）。

> 跨领域提示（供 captain 汇总，不在本领域展开）：渲染管线选型、音频缓冲/采样率、省电策略 → **t3**；C ABI 具体数据格式（像素/采样格式、NST 存档格式、输入位掩码、FDS/BIOS）→ **t2**；MVP 范围与 homebrew 选型 → **t4**；GPLv2 静态/动态链接义务、homebrew 再分发、上架义务 → **t5**。本清单 R7/Q6 与 t5 的 GPL 边界强耦合，建议 captain 在汇总时把「.so 静态链 vs 拆动态边界」作为跨领域合并决策点。
